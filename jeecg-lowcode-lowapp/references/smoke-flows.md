# smoke_flows.py 配置与用法（端到端冒烟）

造最小单据 → 触发流程 → 轮询回读断言 → 收尾清实例、按记录 id 物理删除（断言零残留）。
结构闸门（precheck / check_node_contract / postbuild_verify / app_audit）只查「形状」，
「流程跑起来对不对」「审批任务有没有人收」只有本脚本看得见。

```bash
python "<lowapp>/scripts/smoke_flows.py" --api-base URL --token TOKEN \
  --tenant-id N --app-id A --config smoke.py [--flows flows.py] [--only 用例名,用例名] [--keep] [--include-approval] [--allow-skip]
```

| 参数 | 作用 |
|---|---|
| `--flows` | flow_dsl 写的 flows.py（不是 pb_flows.py），用来识别「新增即进审批」的表；真机也会回读一遍 |
| `--only` | 只跑这些用例；被引用了 `alias` 的前置用例会自动带上。失败时脚本末尾打印 `HINT: --only "…"`，照抄复跑 |
| `--keep` | 不清理（排查用 / 造保留数据）。**实例和记录都会留下**；之后不带 `--keep` 再跑**不会**删它们（运行前已有的记录一条不碰），排查用的要手工删 |
| `--include-approval` | 「新增即进审批」表上没写 `approval` 的用例也跑（收尾照样清本次实例） |
| `--allow-skip` | 有用例被跳过时仍以 0 退出。**默认有跳过 → 退出码 3**，末尾打印被跳过的用例和补跑命令 |

**验收口径：`RESULT fail=0 skip=0`、`OK:cleanup 本次触发的流程实例 N 个 → 清掉 N 个`、`OK:cleanup 全应用 0 行残留`。**
退出码：0 = 全过；2 = 有失败或残留；3 = 没失败但**有用例被跳过**（`skip=1` 不是全绿：被跳过的往往正是网关的非审批分支，2026-09-24 项目申报 R2 的「不立项」就是这么漏的）。

## 配置（smoke.py，只写中文名；字典/选项字段写显示文案，脚本换成落库值）

```python
MARK = 'SMK'                         # 测试数据标记：写进某个文本字段，清理兜底靠它
BASE = {                             # 基础数据：别名 → (表, {字段: 值})，先于所有用例建
    'wh': ('仓库信息', {'仓库名称': 'SMK仓'}),
    'p1': ('产品信息', {'产品名称': 'SMK产品', '成本单价/元': 10}),
}
CASES = [{
    'name': '其他入库单-确认',
    'doc': ('其他入库单', {'入库类型': '期初入库', '入库仓库': '@wh', '仓库编码': '@wh.仓库编码'}),
    'rows': [('其他入库产品明细', '其他入库单', '其他入库产品明细',   # (明细表, 明细回指父单的字段, 父单上的明细字段, {明细字段: 值})
              {'产品信息': '@p1', '产品编码': '@p1.产品编码', '本次入库数量': 10})],
    'trigger': 'update',             # update=先建单与明细，再改 confirm 字段触发；add=明细先建、单据带着明细一次新增触发；
                                     # 'button:作废' 或 {'button': '作废'} = 建好单后点自定义按钮（见「按钮流」）
    'confirm': {'入库确认': '是'},    # trigger=update 时写入的触发字段
    'wait': 20,                      # expect 轮询上限（秒）
    'expect': [('库存实时统计', {'仓库编码': '@wh.仓库编码', '产品编码': '@p1.产品编码'},
                {'其他入库数量': 10, '当前库存数量': 10})],   # (表, 定位条件, 期望值)；期望里写 {'#': 1} = 断言命中行数
    #           定位条件也可以是字符串：'@doc' / '@别名' = 按记录 id 定位那条记录；
    #           '@doc.所属合同' = 本单关联记录字段指向的那条（回写父单时直接定位父单）
    'alias': 'rk1',                  # 可选：给本单据起别名，后面的用例用 '@rk1' 引用
    # 'approval': {...}              # 见下节
}]
```

**取值写法：** `'@别名'` = 那条记录（关联记录字段自动包成 `[id]`）；`'@别名.字段'` = 那条记录的字段值；
`'@doc'` / `'@doc.字段'` = 本用例的单据；`'$now'` = 当前毫秒时间戳。
**更多取值**：`'@别名.id'` = 那条记录的 id（写进「线索池id」这类文本字段）；多条关联一次挂多条写 `['@a', '@b']`。
**删除触发**：`'trigger': 'delete'` = 建好单据（和明细）后删掉它，再按 expect 验删除流程的回写。
**开跑前会整体校验配置**（表名、字段名、别名先后），有错一次列全、不造任何数据。
**expect 的特殊期望值**：`'$today'`（日期是今天，毫秒/字符串都认——按钮/流程写「当前日期」时用）、`'$notempty'`（有值即可）、
`'$empty'`（为空）。期望值写 `'@别名.字段'` 而那条记录上该字段为空时**判失败**（两边都空也「相等」，断言等于没做）。
**公式/汇总字段别传值**：服务端会重算并覆盖（打 NOTE），期望按重算后的值写。
**选人 / 选部门**直接写登录账号 / 部门 id（`'负责人': 'admin'`，多个用逗号），脚本自动包成数组落库（单选也存数组）。
**新增后自动回读**：传入值被服务端改掉（「取关联字段」默认值覆盖、新增流程改写）会打 `NOTE: 表.字段 传入 X，落库 Y`，
不判失败——**造保留数据时逐条看 NOTE**（2026-09-24 担保：费率传 1.8 被产品默认 2.0 覆盖，冒烟全绿、演示数据算错）。
用例按顺序跑、共享 BASE 与前面用例建的数据（「先入库 10 再出库 3 期望库存 7」直接写成两个用例）。

**expect 按记录 id 定位**（2026-09-24 起）：`('担保申请', '@doc', {'审批状态': '已通过'})`、
`('担保合同', '@doc.所属合同', {'合同状态': '已代偿'})`。没有文本标题的表（代偿申请、放款登记…）
不用再挑一个文本列放 MARK 来定位；**MARK 仍要写进某个文本列**——它是清理兜底，
流程派生出来的记录只能靠它扫到。

## 按钮流 `trigger: 'button:<按钮名>'`（2026-09-24 起）

```python
{'name': '反担保措施-登记完成',
 'doc': ('反担保措施', {'反担保物名称': 'SMK房产', '措施状态': '待登记'}),
 'trigger': 'button:登记完成',              # 或 {'button': '登记完成'}
 # 'confirm': {...},                        # 可选：点按钮前先改的字段（同 trigger=update）
 # 'button_params': {'字段model': 值},       # 可选：按钮配了输入参数时传 inputParams
 'expect': [('反担保措施', '@doc', {'措施状态': '已登记'})]}
```

- 脚本按**按钮名**（`/desform/button/list` 的 `label`）找同表按钮的 `processId`，调
  `POST /act/designer/miniDesFlow/api/buttonStartProcess`（processId / dataId / formKey / applyUserId / inputParams
  全走 **query**），`applyUserId` 取当前 token 用户。
- **按钮的显示条件接口不校验**：冒烟点得动 ≠ 界面上看得见，显示条件（`conditionList`）另看。
- 自己调按钮列表：`GET /desform/button/list?designFormCode=<表单编码>`（参数名是 `designFormCode`，写 `desformCode` 报 500）。
- **同一条单据连续点多个按钮**（走完生命周期）：后续用例写 `'doc': ('Bug', '@bug1')` 复用前面用例 `alias` 起的那条记录，
  不再新建；`confirm` 照样可用（先改字段再点按钮）。例：`提Bug(alias=bug1)` → `确认(doc=@bug1)` → `解决(doc=@bug1, confirm={解决方案})` → `关闭` → `激活`。
- 单据表若「新增即进审批」，按钮用例也要写 `approval`（或 `--include-approval`），否则被跳过。

## 审批断言 `approval`（2026-09-24 起）

```python
{'name': '申报-低额50万',
 'doc': ('项目申报书', {'项目名称': 'SMK低额', '申请资助金额': 50}),
 'trigger': 'add',
 'approval': {'node': '部门经理审批',          # 或 'nodes': ['部门经理审批', '部门负责人审批']（任一即可）
              'flow': '项目申报书-申报审批',    # 可选：流程名，同一次触发起多条流程时收窄
              'approve_all': True,            # 可选：断言后把审批逐个按「通过」办结，再跑 expect 验通过后的回写
              # 'reject': ['部门经理审批'],   # 可选：这些节点点「不同意」（审批结果分支走否决支）；写了就会逐个办结，不必再写 approve_all
              'path': ['部门负责人初审', '部门经理复审'],   # 可选：断言逐个办结**经过的节点顺序**（写了 path 即隐含 approve_all；没写 node 时落点 = path[0]）
              'todo': True,                   # 可选，默认 True：断言任务在**当前 token 用户**的待办里
              'wait': 20},
 'expect': [('项目申报书', {'项目名称': 'SMK低额'}, {'申报状态': '待评审'})]}   # approve_all 之后的回写
```

- **断言内容：** 本用例触发后新起的实例里，有一个当前节点 = `node`，且该任务在当前用户 `/act/task/myTodo` 里。
  「任务不在待办」= 审批人配置错（角色名写进 roleIds、`user.` 前缀、表达式解析不到人）——
  这类错 save/deploy/契约/审计**全绿**，这是唯一能看见它的地方。
- **分级审批写两个用例**：阈值以下、以上各一单，分别断言落到对应节点。
- **单据 ↔ 实例的对应**：接口不给单据 id，脚本按「触发前后实例 id 做差」+ 本应用流程 key 对应，所以用例必须串行（脚本本来就是串行）。
- `todo_user`（别的账号的待办）**不支持**：只能查当前 token 用户。办理人不是当前用户时写 `'todo': False`，只断言落点。
- 写了 `approval` 的用例**不会**因「新增即进审批」被跳过。
- **多级审批用 `path`**：`approve_all` 只说明实例最终 ended；`path` 断言经过了哪些节点、顺序对不对
  （高额分支「初审 → 复审」的第二级落点只有它能证明）。日志里 `审批逐个办结 → ended（经过：A → B）` 总会打印。
- 「新增即进审批」的判定：flows.py（`--flows`）+ **真机回读**（启用中的 tableEvent 流程、新增触发、无触发条件、
  含审批/填写节点）。2026-09-24 前真机回读从不存在的 `nodes` 键起步，一个节点都走不到、恒判「不是审批表」——
  不带 `--flows` 时这类用例会直接跑、留下待办；已修（节点链在根的 `childNode` / `conditionNodes`）。

**BASE 里不能放「新增即进审批」的表**（会触发审批、脚本直接退出）。这类基础单写成用例：
`'trigger': 'update'` + `'confirm': {}` + `'approval': {'node': …, 'approve_all': True}` + `'alias': 'so1'`，
后面的用例用 `'@so1'` / `'@so1.编号'` 引用（进销存-速测18：销售订单/采购订单放进 BASE，一条用例都没跑）。

## 清理行为

1. **先清流程实例**：本次运行触发的所有实例（含非审批流程、按钮流的），`GET /act/processInstance/clear?processInstanceId=`；
   失败再退回 `processComplete` 逐个办结。**删记录不会结束实例**——反过来做会在办理人待办里留下打开是空白表单的孤儿任务。
   ⚠️ `processInstance/clear` **会连同业务记录一起删掉**，所以日志常见「N 条记录已随流程实例清理一并删除、删除 0 条」——正常。
2. **再按记录 id 物理删除**（`deleteFromDb`，不进回收站）；本次运行中新出现的记录（流程派生）和带 `MARK` 的派生记录兜底一起删。**运行前就有的记录一条不碰**——含上次 `--keep` 保留的带 MARK 演示数据（运行开始时按表快照 id）。
3. **最后数全表行数**：空应用上跑完应全是 0。「带标记残留 0 条」不等于没留垃圾——流程错建的空行没有文本列，标记扫不到。

## 不要断言的东西

- **计数类汇总**（`记录数/条数/已填计数`）在接口写入的数据上为空（engine-contract #19），求和/平均正常。计数汇总只能在页面验收。
- **别的账号的待办**：见上。

## 纪律

- 复跑只跑失败用例（`--only`）：每个用例的 `wait` 是串行硬等。`--only` 会自动带上**被 `@别名` 引用**的前置用例，
  但不会带「改过同一条记录」的前序用例——期望值是累计值（已拨付 30→90、激活次数 2）的用例复跑时，把前序用例一起点名。
- 结构校验与冒烟结论冲突时以冒烟为准：看到改不掉的结构违例，先花 40 秒跑冒烟。
