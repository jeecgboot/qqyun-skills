# app_spec.json —— 一条命令建完一个应用的**唯一输入**

配合 `scripts/build_app.py` 使用。这是**规格**，不是 dump、不是接口日志。

**核心契约：规格里只写业务语言**（表名、字段中文名、谁关联谁、谁汇总谁）。
控件类型、字典绑定、model/key、公式占位符、流程编排——**全部由脚本推导**，
规格里一个字都不提。理由见文末「为什么不写类型」。

> ⛔ **但「需求原文点名了类型」的字段是例外，必须写死 —— 这条优先于上面那句**（2026-09-21 定论）。
> 上面那句是**省 token 的默认策略**，不是"禁止写类型"。当需求已经写明
> 「XX（金额，2 位小数，单位：万元）」「YY（选择用户，可多选）」时，
> **不写进 `类型`（及对应键）= 把已知信息丢掉、改用启发式去猜**，而 `spec_infer` 猜错是静默的。
> **规则：凡是需求点名了类型的字段，一律写死；推断只在需求没写类型时兜底。**
> 代价只是规格长一点，收益是消灭下面这一整类静默缺陷。

## 最小骨架

下面的领域只是**示意**，照抄的是**结构**，不是表名字段名——按当轮需求替换。

```jsonc
{
  "appName": "设备巡检",

  "菜单顺序": {                   // 可选：导航的分组顺序 + 组内顺序。不写 = 按 forms 书写顺序
    "巡检管理": ["巡检计划", "巡检明细"],
    "基础资料": ["设备档案"]
  },

  "字典": {                       // 应用级字典：字典名 → 选项文案
    "审批结果": ["审批通过", "不通过"],
    "巡检结果": ["正常", "异常", "待复检"]
  },

  "links": [                      // 关联记录 + 带出的他表字段（补丁阶段建）
    {"表": "巡检计划", "字段": "巡检明细", "目标": "巡检明细",
     "条数": "多条", "显示": "表格",
     "带出": ["设备名称", "设备编码", "责任人"]},
    // ⚠️ 需求写「子表（关联工作表）」时，这一档 links 写不出来 —— 上面两行建出的是
    //    普通关联记录（showType:table 只是让它看着像子表）。必须建后单独转，
    //    见本文「子表：关联工作表」+ fast-full-chain.md「③-b」。
    {"表": "目标客户", "字段": "跟进", "目标": "跟进记录",
     "条数": "多条", "显示": "表格", "双向": true,       // 两侧互填 twoWayModel
     "显示字段": ["跟进时间", "跟进结果", "跟进人员"]}   // 只展示、不带出控件
  ],

  "summaries": [                  // 汇总（补丁阶段建）
    {"表": "巡检计划", "字段": "异常总数", "关联字段": "巡检明细",
     "汇总列": "异常数量", "方式": "求和"}
    // 方式只认：求和/合计、平均/平均值/均值、最大/最大值、最小/最小值、计数/记录数/记录数量/条数/总数/数量、已填计数/未填计数。
    // 写了别的（如「最高」）precheck 直接报错 —— 以前会静默当成求和（2026-09-22 销售管理「最大值」两行 0.06 求出 0.12）
  ],

  "layouts": {                    // 表单分节布局（第④段，**补丁之后**统一施加）
    "巡检计划": [                  // 表名 → 分节；「字段」写控件名（= 字段中文名）
      {"标题": "计划信息", "字段": ["选择设备", "巡检计划名称", "计划巡检日期", "责任部门"]},
      {"标题": "巡检明细", "字段": ["巡检明细", "异常总数"]}
    ]
  },

  "flows": [ /* flow_dsl 结构，见 fast-full-chain.md「简流」节 */ ],
  "pages": [ /* build_dashboards 的 pages 结构 */ ],

  "forms": [
    {"名称": "巡检计划", "分组": "巡检管理", "标题": "选择设备",
     "字典": {"巡检结果": "巡检结果"},                // 字段 → 字典名
     "编号": {"巡检单编号": ["XJ", 2, true]},          // 前缀 / 位数 / 是否含日期；给了位数就落 mode:2（mode:1 不补零、位数被忽略，见 fast-create.md「流水号自定义规则」）
     "公式": {"合格率%": "$正常数量$/$巡检总数$"},
     "静态多选": {"产品权限": ["销售", "采购", "赠送"]},  // 不绑字典的多选
     "容器": [{"名称": "关联明细", "页签": ["巡检明细"]}], // 需求点名「用多 tab」时才写
     "字段": ["选择设备", "巡检计划名称", "计划巡检日期", "责任部门", "巡检明细"]}
  ]
}
```

`字段` 里的名字按**六条分支**处理，优先级从上到下：

| 名字出现在哪 | 建法 |
|---|---|
| `links` 的「字段」、或某条 `带出` 里 | 补丁阶段建（关联记录 / 他表字段） |
| `summaries` 的「字段」 | 补丁阶段建（汇总） |
| `forms[].中转字段` 的键 | 补丁阶段建（**隐藏取值信封**，见「中转字段」一节） |
| `forms[].字典` 的键 | 建壳建 select，补丁阶段绑应用字典 |
| `links[].显示字段` 里的名字 | **不建控件**，只填进关联记录的 `showFields`（展示列） |
| `forms[].日期粒度` 的键 | 建壳建 `date`，档位（年份/日期时间…）写在 `dateType` 上 |
| `forms[].静态多选` / `静态单选` / `静态下拉` 的键 | 建壳建 checkbox / radio / **select**（选项写在规格里）。需求写「下拉单选」→ 用 **`静态下拉`**，别用 `静态单选` |
| `forms[].编号` / `公式` 的键 | 建壳建 auto-number / formula |
| `forms[].类型` 的键 | **显式指定叶子类型**，**优先于名字推断**（2026-09-20 新增，见下） |
| 其余 | **建壳按字段名推断叶子类型**（`spec_infer.infer`） |

> ⚠️ **`类型` 是 2026-09-20 新加的「推断纠错」口子** —— 在此之前 `infer()` 猜错时规格**无从补救**，
> 只能建完表再单独改控件（`postfix.py` 里那一大张 `TYPES` 修正表就是干这个的）。
> 写法：`"类型": {"字段名": "中文类型名"}`，只覆盖**叶子类型**（需要选项/关联/汇总/公式的
> 请继续用 `静态下拉` / `links` / `summaries` 那些键，它们带得出额外配置）。可用名（共 16 个，
> **权威来源 = `scripts/spec_infer.py` 的 `TYPE_CN`**，改那份要同步改这里）：
> `单行文本` `多行文本` `金额` `大写金额` `数字` `整数` `日期` `时间` `手机号` `邮箱`
> `选择用户` `选择部门` `地区` `附件上传` `图片上传` `评分`。**写错会报错**，不静默兜底。
>
> ⚠️ **`评分` 曾经不在这份清单里，代价是 2 个字段建错**（2026-09-22 销售管理）：
> `spec_infer` 自 09-21 起就支持 `评分 → rate`，但本文只列了 15 个可用名。作者据此判定
> 「规格表达不了评分」→ 退而写 `"类型": {"客户重要程度": "数字"}` → 建出 `number`，
> 且因为**写的是合法类型名，`precheck` 不报**。**清单与实际能力不符时，以 `TYPE_CN` 为准。**
>
> ⚠️ **闸门是拿「规格」当基准的 —— 规格里没声明的，`app_audit` / `precheck` 看不见。**
> 它们报「违例 0 条」只说明「真机 == 规格」，**不说明「规格 == 需求」**。
> 2026-09-22 销售管理：交付时两道闸门全绿，拿需求原文逐字段比对却查出 **26 处控件类型不符**
> （18 处在第一轮、补全 `类型` 声明后又暴露 8 处）。所以本文末那条「收尾必须跑全量核对」
> **是拿需求原文做基准、不是拿规格**，且**不能用跑闸门替代**。
>
> 典型场景：`技术协议` 这类名字推不出附件（→ 单行文本），在规格里写一行
> `"类型": {"技术协议": "附件上传"}` 即可，不用等建完再补。

> ⛔ **2026-09-21 实测：`spec_infer` 的真实召回率远低于文末那句「严格 95.1% / 真错 0」。**
> 16 表应用逐字段比对（需求声明的类型 vs 落库 `type`）**抓出 24 处不符**，且**全是静默的**
> —— `save`/回读/`precheck`/契约检查一条都不报。两类系统性漏判：
>
> | 名字长这样 | 被推成 | 实际需求 | 本例命中数 |
> |---|---|---|---|
> | `计划资金` `增值税` `附加税` `拜访费用` `个人差旅费用` `费用` | `input` | **金额**（名字里没有「金额」二字就推不出） | 6 |
> | `客户经理` `协同人` `合同签订人` `开票人` `归属客户经理` `销售协同人` `出差人` `员工姓名` `填报人` `部门人员` `其他部门协同人员` | `input`／`select-depart` | **选择用户**（含/不含「人」都不稳，`部门人员` 还被推成部门） | 16 |
> | `排序` | `input` | **数字** | 2 |
>
> **这三类的共同特征是"名字里没有推断词根"，而不是"需求没说"** —— 需求全都写了。
> 所以唯一的防法是**显式写死 + 收尾逐字段比对**，没有"看一眼大概对"的中间态。
>
> ⚠️ **不要只扫「金额」那一类。** 本轮先只发现金额问题、修了 6 个，
> 做全量比对才又抓出 16 个「选择用户」+ 2 个「数字」。
> 比对做法：把需求里点名类型的字段拉成 `{表code: {字段名: 期望控件码}}`，
> 逐表 `query_form` 递归取控件（**必须走 `panes[].list` 与子表 `columns[].list`**）后比对，
> **报告口径是"不符 0 处"**，不是"抽查没发现问题"。
>
> ⚠️ **比对脚本自己也会错，先自证再信结论。** 本轮首跑报「29 处不符」，
> 其中 11 处是脚本把「选择部门」判定写成了 `date`、1 处是把已正确转成子表的控件
> 仍按普通关联记录判 —— **真缺陷只有 18 处**。
> 收尾：任何"批量不符"的结论，先抽 2~3 条人工核对再动手，否则会去改本来对的东西。

> ⚠️ **文件类关键词里的「合同」是后缀锚定的**（2026-09-20 修正）。
> `spec_infer` 原先对「合同」做**子串**匹配，于是 `合同金额` `合同税率` `销售合同名称`
> `销售合同号` `合同相对方` **全被推成附件上传**（该规则优先级高于金额/税率/文本规则）。
> 后果不是「控件难看」——`机会目录.销售合同额(元)` 这个**求和汇总实际在对附件字段求和**，
> 而建表、接口、契约检查全部正常。现在改成**必须以「合同」结尾**才算附件：
> `销售合同`/`采购合同` ✓ 附件，`合同金额`/`合同…` ✗ 走正常推断。

> ⚠️ **`多选` 与 `静态多选` 不是一回事**（2026-09-17 实测踩到）：
> `多选` 只是「**绑了字典的**字段用 checkbox 还是 select」的开关，
> 字段不在 `字典` 里时它**完全不生效**，会落到 `infer()` → `input`（前端是个空文本框）。
> 要「不绑字典的静态选项」必须写 `静态多选` / `静态单选`。
> 本轮 52 表应用里 `产品权限（销售/采购/赠送，可多选）` 就是这么静默变成文本框的。
> **2026-09-17 起 `precheck.py` 会直接拦下这一条**（`多选` 里的字段不在 `字典` 里 → 报错），
> 不用等建完再看控件类型。

> ⚠️ **需求写「下拉单选」→ 必须用 `静态下拉`，不要用 `静态单选`**（2026-09-20 实测，用户回头质问「不是要求下拉单选吗，怎么直接是单选了」）：
> `静态单选` 建壳**固定**落 `radio`（一排横排单选钮）、`静态多选` 固定落 `checkbox`，
> 而 `字典` 那一条虽然建 `select`、却要求选项来自**应用字典** —— 在 `静态下拉` 补上之前，
> 「不绑字典、静态写死的下拉单选」**没有任何一行规格能表达**，作者只能写 `静态单选` 然后拿到 radio。
> 本轮 16 表应用里 25 个「下拉单选」字段（跨 10 张表）全部中招，`precheck` 不报（它只认字段名、不看控件偏好）。
>
> **2026-09-20 起规格支持 `静态下拉`**，与另两档并列：
>
> ```jsonc
> "forms": [
>   {"名称": "目标客户", "标题": "客户名称",
>    "静态下拉": {"客户类型": ["内部客户", "外部客户"]},   // → select
>    "静态单选": {"客户重要程度说明": ["甲", "乙"]},        // → radio（横排钮）
>    "静态多选": {"产品权限": ["销售", "采购"]},            // → checkbox
>    "字段": ["客户名称", "客户类型", "客户重要程度说明", "产品权限"]}
> ]
> ```
>
> 配套：`SELECT()` 工厂已修——静态选项会自动补 `label`（详见下方「为什么静态 select 曾经建不出来」）。

> ⚠️ **需求写「选项：`1 跟进中` / `2 已提报售前申请` …」时，那是 value 与 label 两段，不是一个字符串**
> （2026-09-20 实测，用户回头纠正「机会状态要求显示标签时 设置了 `1 跟进中`，应 value=1、label=跟进中」）。
> 需求里的「**显示标签**」就是在说这件事：下拉显示 label，库里存 value。
> 把它当成单个字符串写 `"静态下拉": {"机会状态": ["1 跟进中", …]}`，会得到 value=label=`"1 跟进中"`
> —— 看着像对的，**列表/下拉显示成「1 跟进中」而不是「跟进中」**，且库里的值也多带了中文。
>
> **选项列表本来就支持 dict 形式，不用建后补丁**（工厂 `_make_options_list` 原生支持，
> 且 `SELECT()` 见到 `label` 会自动把 `showLabel` 置 true）：
>
> ```jsonc
> "静态下拉": {"机会状态": [{"value": "1", "label": "跟进中"},
>                          {"value": "2", "label": "已提报售前申请"}]}
> ```
>
> 判定：选项文案里**数字/代号与中文名用空格或 `/` 连着写**（`1 跟进中`、`A 甲类`）且需求提了
> 「显示标签」→ 用 dict 形式拆开。纯枚举（`男/女`、`大客户/战略客户`）才用字符串列表。
> ⚠️ 改了选项的 value 之后，**引用该字段的流程要同步**：分支条件的 `val`（含 `in/not_in` 的列表
> 逐项）与 `data_update.updateFields[].val` 里存的是旧文案，得一并改并重新 save+deploy。
>
> **已建好的表（用旧规格建的）要补，走这段补丁：**
> 1. **键集照抄本应用一个真实 `select` 控件的 `options`**（如某个绑字典的字段），再抽掉字典专属键
>    `dictCode`/`dictCodeAppId`/`isDictItem`/`remoteOptions`/`remoteFunc`，并把 `remote` 置 `false`。
>    不要凭记忆手写 select 的键集。
> 2. **⚠️ 每个选项项必须补 `label`**：`radio` 的选项项是 `{value, itemColor}`、**没有 `label`**；
>    `select` 的是 `{label, value, itemColor}`。只把 `type` 改成 `select` 不补 `label`，
>    下拉会**空白**——`save` 返回 success、回读 `options` 也非空，只有人打开新增页才看得出来。
>    补法：`{'itemColor': o.get('itemColor'), 'label': o.get('label') or o.get('value'), 'value': o.get('value')}`。
> 3. 回填通用键保住既有配置：`defaultValue` / `required` / `hidden` / `hiddenOnAdd` / `readonly` /
>    `disabled` / `fieldNote` / `placeholder`；再设 `multiple`（需求同时写「可多选」才 `true`）、
>    `filterable:false`、`clearable:true`、`showLabel:true`。
> 4. **同步简流**：这些字段若被已有流程的分支条件 / `data_update.updateFields` / `data_add.formModel` 引用，
>    里面存的 `type`/`valType`/`fieldType` 还是 `radio`，要一并改成 `select` 并重新 `save`+`deploy`
>    （改字段类型不会自动改流程里的副本）。
> 5. 回读断言：`type=='select'` 且**选项里 `label` 缺失数为 0**。
>
> **为什么静态 select 曾经建不出来（根因，改工厂前必读）**：`SELECT()` 工厂用
> `show_label = any("label" in o for o in options_list)` 决定 `showLabel`，而
> `_make_options_list` 对**纯字符串列表**只产出 `{value, itemColor}`（不带 `label`）——
> 于是静态 select 落库 `showLabel:false` 且选项无 `label`，前端下拉是**空白**。
> 修法是在 `SELECT()` 里对静态选项（`not dict_code`）统一 `setdefault("label", value)`；
> `RADIO`/`CHECKBOX` 不走这条、行为不变，绑字典时 `options` 会被清空重填也不受影响。

## `菜单顺序`：导航的分组顺序与组内顺序

```jsonc
"菜单顺序": {"市场及线索管理": ["市场活动记录", "线索池", "线索"],
            "客户及商机管理": ["公海池", "客户", "联系人"]}
```

- **不写 = 按 `forms` 的书写顺序**（分组按首次出现）。`forms` 的书写顺序**不影响建表**
  （关联/汇总都在补丁段才建，不存在「被引用的表要先写」），所以最省事的写法是
  **直接按需求的菜单顺序写 `forms`**；需求另给了「建议创建顺序」时，那只是给人看的，别照着排 `forms`。
- 名字写工作表名或看板名；分组必须与该表的 `分组` 一致。没点名的排在各组点名项之后。
  需求说「菜单隐藏」的表照样点名（通常放各组末尾）—— 隐藏归 `HIDE_MENUS`，顺序归这里。
- `build_app.py` 在**建壳后**与**看板后**各强制重排一次并**回读**，不符即非零退出；
  `precheck.py` 会拦下写错的名字/分组，没写 `菜单顺序` 时把推导出的顺序打成一行提示。

> ⚠️ **为什么必须由脚本强排**（2026-09-21 实测事故，用户截图报障「生成的菜单顺序有问题」）：
> 建壳是**并行**建表，`orderNum` 天然错乱且**会重复**；而且首个分组走 `createFirstGroup`，
> 它的 `parentId` 是 **NULL**、其余分组是 **空串**，后端 `ORDER BY parent_id, order_num`
> → **NULL 的那个分组永远排最前，只改 `orderNum` 修不好**（要先把它的 `parentId` 归一成空串）。
> 当时建壳/补丁/两道闸门全绿 —— 验收只核对了「表在不在对的分组里」，**没有任何一环核对顺序**。

## `日期粒度`：日期控件的档位（年份 / 日期时间 / …）

需求里说「**年份**」「**日期时间**」时，光把它写成日期字段是不够的 —— 控件的**档位**是另一个维度：

```jsonc
{"名称": "机会目录", "标题": "机会名称",
 "日期粒度": {"机会年份": "year", "日期": "datetime"},
 "字段": ["机会名称", "机会年份", "日期"]}
```

合法档位（= `DATE` 工厂的 `date_type` 自述集）：

| 档位 | 显示 | 落库 `options.format` |
|---|---|---|
| `year` | 年 | `yyyy` |
| `month` | 年月 | `yyyy-MM` |
| `quarter` / `week` | 年季 / 年周 | — |
| `date`（**默认**） | 年月日 | `yyyy-MM-dd` |
| `datetime_s` / `datetime_sf` / `datetime` | 年月日时分（秒/带毫秒/标准） | `yyyy-MM-dd HH:mm:ss` |

> ⚠️ **2026-09-20 前整条链路都不透传档位**：创建器 job 认 `dateType`（`desform_creator`
> 把它映射到工厂的 `date_type`），但 `build_app` 从不写它 —— **所有日期字段一律落成
> `options.type='date'`（年月日）**。于是需求写「机会年份（日期选择，**年份**）」的字段
> 显示年月日、「外出时间（**日期时间**）」的也只剩年月日。`save`/`deploy`/回读全绿、
> `precheck` 也不报（它以前不认识这个键），**只有人在新增页上才看得出粒度不对**。
> 现在 `build_app` 会把 `日期粒度` 透传成 job 的 `dateType`，`precheck` 校验档位合法性与字段存在性。
>
> 只管**档位**，不管默认值：「默认当前年」「默认当前时间」是另一回事，见 `高级默认值`
> （date 的默认值写 `advancedSetting.defaultValue`，不是 `options.defaultValueType`）。

## `中转字段`：让明细行「物理带着」一个关联记录（2026-09-21 加）

```python
{"名称": "出库产品明细", "字段": [..., "出库仓库信息"],
 "中转字段": {"出库仓库信息": ("销售出库", "出库仓库")}}
#              ↑本表字段名      ↑顺着这条关联取值  ↑取它的这个字段
```

建出来是一个**隐藏的 `input`**，默认值 = `$<本表那条关联控件的 key>.<父表字段的 model>$`
（设计器里就是「其他工作表」取值）。

**为什么需要它**：流程往台账表写**关联记录**时，手里只有明细行。明细行上原本只有
「XX编码 / XX名称」这类 `link-field` —— 纯文本、**不带指针**，写不进 link-record 列。
挂上中转字段后，每行明细都存了那个记录的 id，流程 `ref()` 就能取到。

**四条约束**：
1. 名字要**同时**出现在 `字段` 里（不然 precheck 报「不在字段列表里」）；
2. `("父表名", "父表字段名")` 的表必须存在、字段必须在它上面；
3. 本表必须**有一条指向该表的关联记录**（`links` 里要有）—— 默认值是顺着它取的；
4. ⚠️ 默认值**只在新增那一刻算**。父单据那个字段为空 → 明细行的中转字段就是空的。

`precheck` 静态查 1~3；`app_audit` 回读真机查「存在 / 隐藏 / 默认值指向对的控件」。
用在哪儿见 `engine-contract.md` 第五节「台账类回写」。

## `带出` 与 `显示字段`：一个是建控件，一个是选列

关联记录（`links`）上有两个容易混的键：

| 键 | 干什么 | 名字要在哪存在 |
|---|---|---|
| `带出` | **建他表字段控件**（把源表字段的值同步到本表），**并顺带**把这些字段填进关联记录的展示列 | 目标表 |
| `显示字段` | **只填展示列**，不建任何控件 | 目标表（本来就要有） |

- **没写 `显示字段` 时沿用 `带出`**（历史行为，两者是同一条声明），所以只写了 `带出` 的关联
  一样有展示列 —— 不必重复写。
- **「要展示几列、但一个带出字段都不需要」时必须显式写 `显示字段`**。典型就是需求里的
  Tabs：`跟进`/`拜访/出差`/`机会` 这些页签要展示 4~6 列，但它们纯属查阅、不带出任何值。
  **2026-09-20 实测**：规格表达不了这一档，作者只能建完手写补丁；而手写时把形状写成
  `[{"field": …, "show": true}]` 是**静默失效**的 —— 引擎只认 `["<model>", …]` 裸字符串数组，
  认不出就回落到**只显示标题一列**，接口全绿，用户看到「要求展示多个字段，怎么只展示了一个」。
- 校验：`precheck` 会查 `显示字段` 的名字在不在目标表上；写错会拦下（不参与补丁的收敛轮，
  因为它不产出字段）。

> 手工补 `showFields` 时（存量表）务必**先 `query_form` 读一个本应用已有的关联控件**看形状，
> 别凭记忆写。另外两个坑：数组里混进 `divider`/`tabs` 这类**非数据控件**的 model 是静默的
> （表格多一列空白）；按**中文名**取 model 时若目标表有**重名控件**（分隔符与多行文本同名时，
> 后者的落库名会被加 `#textarea_…` 后缀），拿到的可能是分隔符，要按 `type` 复核。

> ⚠️ **`带出` 的优先级高于 `forms[].类型`** —— 写进 `带出` 的字段名会被生成器从 `类型` 里
> **整个摘掉**、改按他表字段建。所以需求里的「**金额/单行文本，默认值：取[X]的「Y」**」
> **绝对不能**写进 `带出`：那一档是「普通控件 + 默认值」（默认值走 `postbuild_defaults` 的
> `take()`，建时 copy 一次），误写进 `带出` 就会把它变成 `link-field`、默认值那条随之失效。
> **2026-09-22 实测**：一张表上「金额 + 默认值：取[关联]的[X]」的字段和「单行文本 + 同上」
> 的字段，全被这么落成了 `link-field`（同一个应用里 7 个字段）—— `precheck` / `app_audit` /
> 契约检查**全绿**（规格里那条 `类型` 是被自己摘掉的，不是写错的），
> 只有人肉点开表单才看得出（该自动带出的不再带出、该是静态文本的变成了联动字段）。
> **判据：只有需求里明写「他表字段」的才进 `带出`**；纯展示列改用 `显示字段`。

## `双向`：关联记录两侧互指

需求说「双向关联 / 双向绑定」时写 `双向`：

```jsonc
{"表": "目标客户", "字段": "跟进", "目标": "跟进记录",
 "条数": "多条", "显示": "表格", "双向": true}
```

| 写法 | 含义 |
|---|---|
| `"双向": true` | 目标表里**恰好一个** link-record 指回本表，自动用它 |
| `"双向": "客户目录"` | 指名目标表里回指本表的**那个控件**（对端有多个时用） |

契约（`desform-link-record.md` §六）：A 的 link-record 设 `sourceCode=B_code`，B 的设
`sourceCode=A_code`，**双方 `twoWayModel` 互指对方的 model**（是 model，不是 key），
选择关联时自动在两边建立关系。**只声明一侧即可**，`patch_fields.do_two_way` 会把两侧都写掉。

- **两侧控件都要存在**，所以这一步在主循环**之后**单独跑（对端控件可能由另一张表的补丁建出来）。
- `true` 遇到 0 个或 ≥2 个回指控件都是**歧义，会记缺口而不是猜**。典型：
  `销售合同` 有「客户目录 / 合同相对方1 / 合同相对方2 / 合同相对方3」四个控件都指回
  `客户目录`，此时必须写成 `"双向": "客户目录"`。
- 校验：`precheck` 会查「另一侧有没有指回来的 links」「点名的控件名在不在」，
  歧义（写 `true` 但对端多个）也会拦下。
- ⚠️ **2026-09-20 补这一档之前，规格里根本没有「双向」这个概念** —— 需求点名双向时，
  作者无处可写，`patch_fields` 里 `twoWayModel` 一处都没有，于是**需求被静默降级**：
  接口全绿、`precheck` 全绿，而应用里 `twoWayModel` **一个都没落库**，只能靠用户回看发现。
  同型事故已发生**四次**（`容器`、`静态下拉`、`双向`、`子表`）——**规格语言表达不了的档位，
  最终都会变成静默消失**。四次的共同特征：需求原文写得很清楚，`save`/`回读`/`precheck` 全绿，
  只有用户打开设计器或翻数据才看得出来。

## `记录范围` / `默认带出` / `批量添加`：关联记录行的三档（⚠️ 规格无此档位，只能建后补）

需求里关联记录那一行常带三样，`links` 的键（`表/字段/目标/条数/显示/双向/显示字段/带出`）**都写不进去**：

| 需求原文 | 落点 |
|---|---|
| `记录范围：【A】等于本表【B】` | `options.filters = [{matchType:"AND", rules:[{model:源表A的model, rule:"EQ", valueType:"field", value:[本表B的model], sqParam:{type,rule:"eq"}}]}]` |
| `默认 【关联字段】【字段】` | `advancedSetting.defaultValue = {type:"compose", value:"$本表关联控件key.源表字段model$", …}` |
| `手动添加、批量添加，绑定子表中的【X】字段` | `options.createMode = {add:true, select:true, params:{selectLinkModel: 子表里X字段的 model}}` |

- ⚠️ **2026-09-20 实测：前两档当年就是「双向」那一型事故**。24 表应用里 **9 个记录范围全丢**（`filters` 在各补丁脚本里一次都没出现）、**4 个子表 createMode 全丢**（`createMode.select` 恒 `false`、`selectLinkModel` 空）；默认值靠**手写补丁清单**兜底，38 条里漏抄 1 条（漏了不报错：字段在、类型对、save 全绿）。
- `sqParam.type` 按**源表**字段类型算（`link-field` 取 `options.fieldType`、`date` 取 `options.type`），**不是**本表字段类型。
- 写法照「子表」那一档：**建后补 + 交付说明里显式留待办**，`precheck` 不报这三档。细节见 `desform-link-record.md` 二-b / 三 / 五。

## `子表`：关联工作表（⚠️ 规格无此档位，只能建后转换）

需求写「XX（**子表**，关联工作表「YY」，展示字段 …）」时，`links` 表达不了这一档 ——
`条数`/`显示` 最多写出「多条 + 表格」，落库是**普通 `link-record`**：
顶层无 `isSubTable`、`model` 是 `link_record_*`、`twoWayModel` 空。
`create_linked_worksheets.py` 的 `link` 与 `add_link_record.py` 同样不产出子表形态。

**写法**：照常写 `{"条数":"多条","显示":"表格"}`，但要在交付说明里显式留一条
「XX 需建后转子表」的待办 —— **`precheck` 不报这一档**（它只认字段名与控件偏好）。
转换 4 步 + 自查见 `desform-link-record.md`「二-a」，全链路的落点见 `fast-full-chain.md`「③-b」。

> ⚠️ **别被 `显示:"表格"` 骗了。** `showType:"table"` 让明细区就是一张表格，**看着就是子表**，
> 但设计器面板里它仍叫「关联记录」。2026-09-20 实测：一份提示词写全了
> 「子表，关联工作表「客户联系人」，展示字段 客户联系人/手机号/座机号/职务/微信/备注」，
> **6 个展示字段一个不差地落进 `showFields`，唯独「子表」这一档整条丢了** ——
> 越是其余全对，越说明丢的不是解析错误，而是规格语言里没有这个位；
> 那 16 张表 53 个关联控件里 `isSubTable` 是 **0 个**。

## 为什么规格能不写类型

一份 50+ 表应用的规格有 1000+ 个字段。每个都写类型 → 约 **32k token，超过单次输出上限**，
只能拆多次写——这正是「生成慢」的主因。只写名字 → 约 19k token，一次写完。

代价是推断会错。实测：把**全部**字段交给命名推断只有四成多命中——
因为其中三四成是关联/他表/汇总，**纯语义，名字里看不出来**。
剥掉这些语义类、只推断叶子后：**严格 95.1% / 等价 100.0% / 真错 0**。
剩下的是 money↔number、input↔textarea 这类**外观差异，不影响应用可用性**。

## 写规格时的四条硬规矩

**1. 斜杠是「与」，不是字段名的一部分。**
`设备名称/编号` = 设备名称、设备编号。真实字段名里确实有斜杠（`含税金额/元`），
但规格**从不写 `/元` 这类单位后缀**，所以在规格命名空间里斜杠一定是「与」。

**2. 带出字段必须是目标表里**真实存在**的名字。**
写规格时按**目标表**核对，别照抄需求文档或上游单据的显示名。常见的对不上有三类：
- 带限定前缀：写 `设备档案.巡检设备名称`，该表只有 `设备名称`
- 成对互串：写 `巡检计划编码`，实际是 `巡检计划编号`
- 子串包含：`检测报告附件` ↔ `检测报告附件上传`

对不上时 `patch_fields` 会报 `（是否想写：…）`，**照着改**。别放过。

**3. 表名全用中文，code 交给脚本。**
`build_app.py` 生成纯 ASCII 的 `code`。**code 必须 ASCII**：它出现在
`/desform/api/fields/<code>` 这类**路径**里（不是 query），而 `bi_utils._request`
只 urlencode params、不编码路径——中文 code 会直接 `UnicodeEncodeError`，
看板阶段整段失败且**页面建出来是 0 组件**（2026-09-16 实测）。

**4. 流程排在灌数之后（灌数本身是例外，默认不跑）。**
规格里 `flows` 和 `forms` 的书写顺序无所谓，但**执行顺序**由 `build_app.py` 固定为
字典→建壳→补丁→布局→**灌数（仅用户要求时）**→流程→看板。
**默认不灌数**：`--rows` 默认 `0`，那时这一段整段跳过，顺序自然退化成「…布局→流程→看板」。
要灌数的理由见 `fast-full-chain.md` 文首 ⚠️：流程建好后 `add_data` 会触发级联写，实测 1h4m + 后端崩。

**流程写在哪里？两个入口都收（2026-09-17 打通）。**

| 你手上是什么 | 怎么喂 |
|---|---|
| `flows.py`（`flow_dsl` 写的，**文档各处推荐的那种**） | `build_app.py … --flows flows.py` |
| spec 里的 `flows` 数组 | 不写 `--flows`，`build_app` 自己拼成 flows.py |

> ⛔ **需求写了「子表」（要走建后套件 `SUBTABLES` 转换）时，`build_app` 不要带 `--flows`、spec 里也不要放 `flows`**：
> 转子表会换掉明细控件的 model，先建好的流程条件/取数就悬空了，而 `save/deploy/契约/app_audit` 全绿、只有冒烟抓得到
> （2026-09-22 销售管理 R2 实测）。正确顺序：`build_app` → 建后套件（含 SUBTABLES）→ `postbuild_probe` → `build_flows`。
> 已经建了的话 `postbuild_struct` 会打 `TODO: 流程「X」引用了已换名的子表控件 → build_flows --update --only "X"` 并 exit 2。

> ⚠️ 老版本**只认后者**，而且不打 `--flows` 时那句日志是
> 「规格里没有流程，跳过」—— 按文档写完 `flows.py` 的人会以为流程建好了，
> 实际建出来 **52 表 0 流程**，还得再单独跑一次 `build_flows`。

**5. 流程要用到的字段，必须在明细表上物理存在。**

简流的子流程上下文**只能读本行字段**——`ref()` 与 `cond` 都取不到父单据的值。
所以「被流程逐行处理的明细表」必须自带它需要的键。2026-09-16 实测：漏一个键，
流程能发布、能跑，但**一行都不写**。

**这份键清单靠逐条流程推导，不照抄任何既有表：**

1. 列出每条「主表触发 → 取多条明细 → 逐行调子流程」的流程；
2. 读它的子流程节点，把 **`ref()` / `cond` 里用到的每个字段**抄下来；
3. 拿这张清单核对该明细表的 `字段`——**缺哪个补哪个**。补法只有一种：
   再建一条指向来源表的关联记录并 `带出`（要拿关联记录本身，就把关联字段名写进 `带出`）。

示例（设备巡检，仅示意）：巡检明细的子流程要按设备定位、并回写父单，则该明细表的 `字段`
里要有 `设备档案`（关联记录本身）+ `设备名称` `设备编码`（定位键）+ `巡检单编号`（回写父单）。

配套约束（动笔前先读 `references/engine-contract.md` 那一页）：
- 「没有就新建」用 `empty="新增"`，且紧跟的 `update` **必须把定位键一起写进去**
  （新建出来是空记录）。定位键 = 你用来唯一区分一行的那几个字段，按第 2 步的 `cond` 定，
  全流程保持一致。
- **流程里做不了算术**：累加/扣减用 `inc()/dec()`；合计/余额这类派生量
  定义成**工作表公式字段**，流程只写基础计数。
- 跨表回写靠**两侧同名同值字段**做 `cond`（桥字段必须在两张表里都存在且同名）。
- **动真机之前先跑** `python scripts/precheck.py --spec app_spec.json [--flows flows.py]`
  —— 纯静态、不联网，能拦下公式占位符 / 带出字段名 / 看板透视空 val / 查询面板跨表。

## `layouts`：表单要分节，别让它平铺

**不给 `layouts` 会怎样**（2026-09-17 实测的事故）：建壳阶段把字段两两配对，
**补丁阶段是一个字段一张卡地追加**，于是最终形态是「一长串单字段卡、零分隔符」——
而线上进销存模版是 `divider「采购订单信息」→ card[3 字段] → …`
（366 张卡里 240 张正好 3 字段）。用户看到的「表单布局和模版不一样」就是这件事。

所以 `layouts` 不是可选项，是**规格的一部分**：

```jsonc
"layouts": {
  "采购退货": [
    {"标题": "采购订单信息", "字段": ["选择采购订单", "采购订单名称", "采购订单编码",
                                    "供应商名称", "供应商编码"]},
    {"标题": "退货产品明细", "字段": ["退货原因", "退货产品明细", "退货产品总数"]}
  ]
}
```

- **标题** → 该节前面插一个 `divider`（段标题）。**标题留空串则不插分隔符，只分组**——
  分组本身照旧生效（控制每卡字段数与字段顺序），只是不画线。

> ⚠️ **`标题` 只在需求点名了分隔符时才写。** `layouts` 里的分节是**布局手段**，
> 不等于需求里的「分隔符」——需求写「XX（分隔符）」才画线，没写就别画。
> 2026-09-18 实测：一份需求里 16 张表只有 6 张点名了分隔符，作者给**每张表每个分节**
> 都填了语义标题（「客户信息」「归属与分级」…），结果 10 张表凭空多出 29 条分隔线，
> 用户直接问「怎么多加了好多分隔符」。**需求没点名时，分节照写、标题一律留空串。**
- **每卡字段数**默认 3，`regroup_layout.py --per-card N` 可改；卡内自动均分列宽
  （3 个 → `autoWidth 33.333`，2 个 → 50，1 个 → 100，与模版一致）。
- **名单顺序 = 界面字段顺序**（平台无独立排序字段，见 `desform-design-json-schema.md`）。
  **夹在字段中间的选项卡**（「商机详情」「客户信息」「合同明细」这类）必须按声明位置进名单——
  落库后它就是一个 `tabs` 控件，位置由它在顶层 `list` 的下标决定；追加到末尾会把原本
  排在它后面的字段顶到前面（2026-09-20 用户按规格逐表核对时发现）。
- **名单不必穷尽**：没点名的字段按原顺序收在最后，不会丢。
- **写了表上没有的字段名 → 直接报错并列出该表现有控件名**，不静默少放一个字段。
- 宽控件（`textarea`/`imgupload`/`file-upload`/`tabs`/`editor`…）自动独占整行，不塞进卡片。
  **「整行」的判定见 `desform_utils.is_wide_widget`**：除上列类型外，
  **表格模式的关联记录**（`link-record` + `showType=table`）与**设计子表**也独占整行——
  ⚠️ **这是默认规则，规格不点名也照做**（它们内部渲染的是整张表，按每卡 3 个均分会压成 33% 宽）。
  只对 `showType=table` 生效；卡片/下拉模式的关联记录（`showMode` 单条/多条与它无关）仍是普通字段宽。
  ⚠️ **手工重排卡片时同样要按 `is_wide_widget` 判定摘出来单独成卡**——只按规格的
  整行/半行/1-3 槽位凑行、不跑宽控件判定，会把表格模式的关联记录重新压进 3 列卡
  （2026-09-20 实测：客户、合同订单各有 5 个 / 4 个被压进 3 列卡，用户指出后返工）。

改已建好的应用时不用整轮重跑，单独一段就行：

```bash
python scripts/regroup_layout.py --api-base ... --token ... \
  --tenant-id N --app-id A --config layout.json [--form 表名] [--dry-run]
```

> 别把**别的环境**的字段名抄进 `layouts`：同一份需求在不同轮次里字段名会因命名规则
> （禁单位后缀 `/元`、斜杠=「和」）而不同。按**本应用现有控件名**写。

## `容器`：把点名的字段装进 Tabs

需求写「**这几个字段用多 tab**」时才写容器。写法：

```jsonc
"forms": [
  {"名称": "目标客户", "标题": "客户名称",
   "容器": [
     {"名称": "关联明细",                        // Tabs 控件的名字
      "页签": ["跟进", "拜访/出差", "机会"],      // 字符串 = 页签名就是字段名，装这一个控件
      "新增时隐藏": true}                        // 可选；不写就不动控件原有的显隐
   ],
   "字段": ["客户名称", "客户简称", "跟进", "拜访/出差", "机会"]}
]
```

`页签` 的元素两种写法：

| 写法 | 含义 |
|---|---|
| `"跟进"` | 建一个叫「跟进」的页签，里面装控件「跟进」 |
| `{"相关记录": ["跟进", "机会"]}` | 建一个叫「相关记录」的页签，里面装两个控件 |

四条规矩：

1. **容器固定落在表单末尾。** 这是刻意的——`apply_group_layout` 把没点名的顶层控件
   一律收在最后，所以「容器跟着第一个字段的原位置走」会**第一次建在表单中部、重跑一次
   就漂到末尾**（静默漂移）。固定末尾则首建与每次重跑完全一致。要调位置就调 `layouts`
   的分节顺序，别指望容器插在中间。
2. **容器字段不要写进 `layouts` 的任何分节。** 容器段会把控件从卡里摘走，那一节就只剩
   一条光秃秃的分隔线 —— `precheck` 会直接报错拦下。不写进分节即可（它们会落进
   `rest`，正好被容器收走）。
3. **只搬运，不重建。** 控件 dict 原样搬进页签，`key`/`model` 一个字节都不改 —— 重建会换
   model，把双向关联（`twoWayModel`）和上游引用一起打断（engine-contract #13）。同理
   「表格模式 / 多条」这些语义由 `links` 声明、补丁阶段已设好，容器**不会**再改它们。
4. **重跑幂等。** 同名容器已存在就整组跳过，不会重复建。
5. **页签名 == 控件名时，容器自动把该控件的标题关掉**（顶层 `hideTitle=True`，2026-09-20 补）。
   否则页签里会先画一遍页签名、再画一遍**同名**的控件标题 —— 用户看到的就是「tab 中多了个标题」。
   规则**只在同名时生效**：一个页签装多个控件（`{"相关记录": ["跟进", "机会"]}`）时页签名是
   概括性的，各控件标题是唯一的区分，**不能**关。这条已在 `group_into_tabs` 里做掉，写规格不用管。
   ⚠️ 手工补这个属性时注意 `hideTitle` 在**控件顶层**，写进 `options` 是静默无效的。
5. **任何遍历表单设计的代码都必须走 `panes`。** 容器里的控件**仍属主表字段**，
   只走 `list`/`columns` 的遍历**根本看不到它们**——对上层就等于「这个字段不存在」，
   后果分两种，都是静默的：
   - `patch_fields` → `find_widget` 找不到 → 在顶层**再建一份**（字段重复）
   - `postpatch` 之类的属性补丁 → 整组跳过（显示字段 / 新增时隐藏 / 双向关联**全空**）

   > ⚠️ 2026-09-18 实测（就在实现本特性时踩到）：`patch_fields.iter_widgets`、
   > `regroup_layout.iter_widgets` 和项目侧的补丁脚本都只走 `list`/`columns`。
   > 后果是重建出来的 目标客户 三个页签控件 `showFields=0` / `hiddenOnAdd=False` /
   > `twoWayModel` 空 —— 而需求要的是 5/5/6 个展示字段 + 新增时隐藏 + 双向。
   > 三个文件已修。`desform_utils.get_form_fields` 的 `extract` 一直是走 panes 的，以它为准。
   >
   > **别 yield pane 本身**：页签的 `name` 就是页签名，常与字段同名（页签「跟进」里装着
   > 控件「跟进」），把它吐出去会让按名字找控件的代码抓到页签而不是控件。

> ⚠️ **为什么这条要单独写一节**：规格语言以前**根本没有「容器」这个概念** —— 每个字段
> 只有「一个名字 → 一个平铺控件」这一条出路。需求点名「用多 tab」时，作者只能把控件
> 平铺建出来、事后再手工搬，而且 `precheck` / 建表 / 补丁**没有任何一环会告诉你 tab 没建**。
> 2026-09-18 实测：一份需求点名 3 个字段用多 tab，应用建完是三个平铺的关联记录，
> 接口全绿、预检通过，直到用户回头问「Tabs 布局空间可以加吗」。**需求被静默降级**，
> 跟这一年来踩过的其余坑是同一个病。现在 `precheck` 会拦下容器字段名写错、重复点名、
> 同名容器、同名页签、页签空着，以及「容器字段又写进了 layouts 分节」。

## `必填` / `选项`：字段级的校验与控件选项

```jsonc
"forms": [
  {"名称": "目标客户", "标题": "客户名称",
   "必填": ["客户名称", "所属客户"],                      // 建壳时写 options.required + rules；关联记录（links 里的字段）也能写，补丁阶段建控件时落 required
                                                          // 他表字段 / 汇总不能必填（precheck 报错）
   "选项": {"附件": {"multiple": true, "length": 10}},    // 直接写进控件的 options
   "字段": ["客户名称", "附件"]}
]
```

**`选项` 只收 options 级键**（`desform_utils._VALID_OPTIONS_KWARGS`）：
`fieldNote` / `hidden` / `hiddenOnAdd` / `disabled` / `placeholder` / `unique` /
`readonly` / `inline` / `showLabel` / `useColor` / `filterable` / `clearable` /
`precision` / `allowHalf` / `allowScan` / `scanEditable` / `multiple` / `length` /
`unitText` / `unitPosition`。

> ⚠️ **金额/数值的「单位」用 `unitText` 声明**（2026-09-20 加）：需求写
> 「计划资金（金额，2 位小数，**单位：万元**）」时，规格要写成
>
> ```jsonc
> {"名称": "机会目录", "选项": {"计划资金": {"unitText": "万元", "precision": 2}, …}}
> ```
>
> 工厂对 `money` 默认 `unitText='元'`，**不声明就一律显示「元」**——用户会直接问
> 「单位是万元，怎么还是元」。`unitPosition` 控制单位在前/后（`suffix` 默认 / `prefix`）。
> `precision` 是小数位（需求「2 位小数」→ `2`）。
> ⚠️ 这两个键是 2026-09-20 才进白名单的：在此之前写进 `选项` 会被判「非白名单参数」
> **静默丢弃**（`make_widget` 只打一行警告），控件照旧显示「元」。
>
> ⛔ **2026-09-21 实测更正：`unitText` 至今仍会被静默丢弃，而同一对象里的 `precision` 会落地。**
> 规格写 `"预计机会金额": {"unitText": "万元", "precision": 2}`，回读是
> `unitText='元'`（工厂默认）+ `precision=2` —— **一组选项里一个生效一个不生效**，
> 所以「precision 对了就以为这组选项生效了」是错的判据。
> 单位类的验收口径只有一条：**逐字段回读 `options.unitText`，与需求原文对照**
> （只有写明「万元」这类非默认单位的才要查）。
> 已建好的表补单位：`query_form` → 改该控件 `options.unitText`/`unitPosition` → `save_design_from_file`
> + `save_auth_from_design`（**不要**改规格重跑建壳——建壳对已存在的表是 `[阻止]` 跳过）。

> ⛔ **金额字段的「类型推断」和「单位」是两个独立的坑，别只修一个**（2026-09-21 实测）。
> `spec_infer` 靠字段名里的「金额」二字推 `money` —— 名字里没有的（如 **`计划资金`**）会落成
> **`input`（单行文本）**；而 `选项` 里的 `precision` 照样生效，**看起来像个配好的数字字段**。
> `类型` 覆盖是唯一的口子：`"类型": {"计划资金": "金额"}`。
> **动笔时把金额类字段逐个点名核一遍 `类型`**，不要只覆盖"名字看着不像金额"的那几个。
>
> ⚠️ **它还会连带把简流条件写成错误的控件族**（比控件难看严重得多）：
> 流程条件里存着 `type`/`valType`，由 `Resolver.family()` 按**设计里的真实控件类型**解析。
> 字段是 `input` → 条件存成 `type:'input'`，而 **`input` 族没有「小于 / 大于等于」这类数值规则**
> → **条件恒不成立**；`inclusive` 又是「一条都不命中就永久卡在网关上」
> （`bpm_status=2`、记录在列表里被锁、没有编辑按钮，且 `/act/task/list` 为 0，看不出是流程问题）。
> 本例：「计划资金 小于 200 / 大于等于 200 / 为空」三条分支**全部**存成 input 族，
> 只要计划资金非空 → 三条全不命中 → 必卡；而且 save/deploy/回读/契约检查**全绿**。
> **修法必须两侧一起改**（node-contract §9.3）：① 控件 `type` 改 `money`（就地改，**保留 `key`/`model`**）；
> ② 回读该字段被引用到的**所有流程**，把 `conditionGroup[].queryItems[]` / `updateFields[]` /
> `data_add.formModel` 里的 `type`/`valType`/`fieldType` 一并改 `money`，再 save + deploy。
> **只改字段侧 = 静默故障**（两侧不同步时 save/deploy/回读照样全绿，条件照旧不命中）。
>
> ⚠️ **这不是个别现象，是系统性的——按名字推金额的召回率很低。** 16 表应用实测：
> 需求点名「金额」的字段里 **6 个**落成了 `input`：`计划资金`、`增值税`、`附加税`（名字里没「金额」）、
> `拜访费用`、`个人差旅费用`、`费用`（词根本不在推断词表里）。**只有 `预计机会金额` 这种带「金额」的才推对。**
> 收尾必须跑一次全量核对：把需求里所有标「金额」的字段名拉成清单，**逐个回读实际 `type` 是否 == `money`**。
> （别用「有没有 unitText」当判据 —— 落成 `input` 的字段连 `unitText` 都没有，扫不出来。）
>
> ⛔ **最贵的连带后果：汇总的「求和源列」会变成文本列。**
> `拜访费用`/`个人差旅费用` 是 **4 条汇总**的求和源（目标客户 2 条 + 机会目录 2 条）。
> 源列是 `input`（文本）时，`inner-sum` 对文本列求和 —— 接口全绿、汇总控件长得也对，
> **算出来的数是错的/空的，只有人对着明细手算才发现**（同型事故见 `desform-widget-options.md`
> 汇总节「对附件字段求和」）。改完源列类型后，**汇总控件不用动**（它按 model 引用，model 未变），
> 但要**回读一遍汇总的 `options.field` 仍能命中源表当前列 model**。

> ⚠️ **分隔符等「非字段控件」同样要写进 `选项`（2026-09-20 实测漏改）：** 需求常常把标注
> 挂在分隔符上——「**商务信息（分隔符 新增时隐藏）**」「销售信息（分隔符 新增时隐藏）」。
> 这类控件**不在「必填」的语境里、也不像字段**，写 `选项` 时最容易整组漏掉：同一批字段
> （商务谈判方式 / 线索成本 / 拜访费用（元）…）`hiddenOnAdd` 全是 `true`，**只有四个分隔符是
> `false`**，用户看到的就是「新增表单里空着一排分节标题」。
>
> **判断口径：需求里凡写了「新增时隐藏 / 默认隐藏 / 禁用 / 只读」的控件，不论类型
> （分隔符 / Tabs / 富文本 / 附件 / 字段），都要在 `选项` 里落一条对应键**
> （`hiddenOnAdd` / `hidden` / `disabled` / `readonly`）。分隔符的 `DIVIDER()` 支持
> `hiddenOnAdd`，`make_widget` 的白名单里有它，**能力不缺、只是规格没写**。
>
> **这类漏改是静默的**：`save` / `deploy` / 审计全绿、字段一个不少，只有打开新增表单才看得见。
> 交付前把需求里所有「新增时隐藏 / 默认隐藏 / 禁用 / 只读」的控件名拉成清单，逐个对到落库
> 设计的 `options` 上——这是**逐条属性核对**，不是计数核对（`hiddenOnAdd` 的总数对得上也可能
> 是别的字段替你凑齐了）。
>
> **核对时的已知误报，别当缺陷改**（2026-09-20 全表核对 92 一致 / 10 不符，其中 9 条是误报）：
> - **关联记录的「多条」不是 `options.multiple`**，而是 `options.showMode: "many"`。规格里写
>   `multiple` 本来就不适用，落库查不到 `multiple` 属正常。
> - **汇总统计（`summary`）/公式控件不吃 `precision`**（需求没写小数位时更不用管）；落库没有
>   这个键不代表显示有问题。
> - 需求写「（…默认隐藏）」、「展示字段 A、B、C，默认隐藏」时，**隐藏的是那个控件本身**，
>   A/B/C 只是它带的展示字段名——别去按 A/B/C 找控件。

⚠️ **不要往里写 `dateType` / `mode` / `expression` 这类**：它们是**建壳器级的抽象**，
工厂内部会做翻译（`dateType` → `options.type='datetime'`）。当成 options 级直接写进去，
只会往控件里塞一个**设计器不认的键**——2026-09-18 实测，线上日期控件是
`options.type='datetime'`，`dateType` 根本不存在。`precheck` 会直接拦下这类键。

> ⚠️ **这两个键是 2026-09-18 补的**，因为在此之前规格**表达不了它们**：
> `required` 在 `build_app` 的 spec→建壳 链路上没有消费者，控件级选项连书写位置都没有。
> 后果是**静默**的 —— 需求写「客户名称必填」「附件最多 10 个」，应用照建、接口全绿，
> 只是字段不是必填、附件没有个数上限。实测全应用 15 个附件字段**无一例外**是
> `multiple=false, length=0`。
>
> **已建好的表靠重跑建壳是改不动的**（建壳对已存在的表打 `[阻止]` 跳过），
> 要用 `regroup_layout.py` 那样的「读设计 → 改 options → 写回」路径补。

## 什么时候不该用编排器

- 表数很少（<10）且要精细控制每一步
- 要做的定制超出规格能力（自定义按钮、复杂联动查询、子表转工作表等）

这时按 `fast-full-chain.md` 的 ①–⑧ 手写各段，但**仍可用本规格作为中间表示**：
`build_app.py --dry-run` 会打印它解析出的建壳计划，用来核对。
