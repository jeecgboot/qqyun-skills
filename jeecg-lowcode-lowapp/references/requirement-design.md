# 一句话建应用：需求设计层（先设计 → 用户确认 → 再建造）

**什么时候读本页：** 需求**没写到字段级**——「建一个 XX 系统」「类似禅道的任务管理」「给我们做个担保业务系统」，
或只列了模块/几句业务规则、没逐表列字段。需求已逐表列字段（像 `app-prompt-skeleton.md` 那种）时**跳过本页**，
直接走 `fast-full-chain.md`。

**产出：** 工作目录里一份 `design.md`（需求说明 + 功能设计），**发给用户确认**，确认后再照常写
`app_spec.json` / `flows.py` / 盘配置，走 `fast-full-chain.md` 的建造链路。本页只管「把一句话补成设计并确认」，建造规则一条不改。

> ⛔ **设计完先给用户确认，确认了再建**（2026-09-24 用户：「设计还不稳定，出需求说明和功能设计的时候让用户确认下」）。
> 设计是你替用户补的，而你**不了解这家客户的实际业务**：「类似禅道」建成带预算审批的系统、Bug 表堆了 20 个字段，
> 都是闸门和冒烟抓不到、用户一看页面就否掉的。建之前让用户看一眼设计，比建完返工便宜得多。
> · 确认的是**整份设计一次看完**（格式见第「一·五」节），不是零零散散反问一串问题；
> · 发出去后**结束本轮回复、等用户回话**。用户说「可以 / 确认 / 开始建」→ 建；提修改 → 改 `design.md` 再发一遍（只列改了什么）；
> · **只有两种情况不等确认**：用户明确说「直接建 / 不用确认」；或是无人值守的测试代理（提示词里写明不等确认）。

---

## 一·五、给用户确认（设计写完、动手建之前）

把 `design.md` 整理成下面这个样子发给用户（**一屏能看完**，用业务话，不写 model/字段类型代码）：

```markdown
## 需求说明
- 系统定位：<给谁用、解决什么问题，一句话>
- 用户角色：<谁会用，各做什么>
- 日常场景：<5~8 条，角色视角，例：测试提 Bug 指派给开发 → 开发修好点「解决」→ 测试验证后关闭>

## 功能设计
- 表与字段：<每张表一行：表名：字段1、字段2、……（为什么是这些）>
- 表之间的关系：<Bug 属于项目；项目里能看到它的任务和 Bug……>
- 流程：<什么时候触发 → 做什么；审批谁审、金额门槛>
- 看板：<看什么数>

## 省略的（要就说一声）
<拿不准所以没建的字段 / 表>

## 需要你定的（最多 3 个）
<真正影响设计走向的问题，如「Bug 要不要审批」「需要工时统计吗」>
```

- 用户回「可以」就按它建；用户改了就**以用户的话为准**更新 `design.md`，再发一遍改动点。
- 「需要你定的」给出你的默认选择（「不回复就按 A」），别出开放题。
- 交付时报告里写「设计已经用户确认（确认时间 / 改了哪些）」。

---

## 一、设计步骤（按顺序，一步都别跳）

### 0. 先认参照产品 / 行业，再定对象

一句话里点了参照产品（「类似禅道」「像 Jira」「Teambition 那样」「类似用友」），**按那个产品的核心对象和主流转设计**，
不要退回成「通用企业审批系统」。常见参照：

| 参照 | 它本质是什么 | 核心对象 | 主流转靠什么 |
|---|---|---|---|
| 禅道 / Jira / 缺陷管理 | **软件研发 + Bug 跟踪** | 核心只有**项目/产品、Bug（或任务）**；需求、迭代、用例是团队用到了才加 | **状态流转 + 指派**：提 Bug → 处理中 → 已解决 → 已关闭（可重新打开）；日常只填标题、描述、指派给、优先级 |
| Teambition / Trello / 看板 | 协作任务看板 | 项目、任务列表/阶段、任务、子任务、标签 | 拖动阶段 = 按钮改状态、执行者、截止日期 |
| 采购 / 报销 / 合同 / 借款 / 担保 / 申报资助 | 花钱或管钱的业务 | 申请单、合同、付款… | **金额分级审批** |

**点了多个参照产品、而它们重心不同时，「以谁为主」必须放进确认稿「需要你定的」第 1 条**（例：禅道=以 Bug 为主，Teambition=以任务为主）。2026-09-24「类似禅道和 Teambition 的任务管理系统」被设计成 Teambition 式任务协作、Bug 表进了省略项，用户确认时纠正：「我需要的是 BUG 系统管理，以 BUG 为主，软件」。系统名（「任务管理系统」）不等于业务重心，别据此替用户选。

**没有钱的业务不要造钱**：研发、缺陷、任务、工单、巡检、考勤这类，**不要为了凑「金额审批」「金额看板」给项目/任务加
预算、费用字段**（2026-09-24「类似禅道」被建成带「项目预算 ≥ 50 万走领导审批」的系统，用户明确说不对）。
这类业务的数值是：工时、数量、严重程度/优先级（字典）、Bug 数、解决时长。

### 1. 定对象（按日常场景定，宁少勿多）

**表的数量由日常场景决定，不凑数**：协作/研发工具类常见 3~8 张，管钱管合同的业务（担保、申报、进销存）环节多才到 10~15 张。
5~12 条流程、1~2 个看板，目标建造墙钟 ≤ 20 分钟。
对象按四类找，**日常场景用得上才建**（明细行、台账很多业务根本不需要）：

| 类 | 是什么 | 例（类似禅道的研发 / Bug 管理） |
|---|---|---|
| 基础资料 | 被别人选的主数据 | 产品、模块、版本 |
| 业务单据 | 有生命周期、要流转/指派的单 | 需求、任务、Bug、测试单 |
| 明细行 | 单据下的多行 | 测试用例步骤、Bug 处理记录 |
| 台账/汇总 | 被流程回写的结果 | 版本 Bug 统计、人员待处理数 |

行业惯例里「一定会有」的对象不要漏（担保必有「反担保措施」「保后检查」「代偿」；申报必有「评审/专家打分」
「立项结果」）。宁可少建一张冷门表，也别漏主链路上的一环。

### 2. 字段：按业务场景设计，实用不啰嗦

**每个字段都要答得出「谁、在哪一步填或看、拿它做什么」**（被流程判断/回写、被列表筛选、被看板统计、办事的人要看）。
答不上来的**不建**——多一个没人填、没人看的字段，就是多一行噪音（2026-09-24 用户看 Bug 表：「是不是太啰嗦了，字段不需要那么多」，
20 个字段里所属项目/关联任务/来源用例/解决说明这些，场景里根本没人用）。

- **从业务场景倒推字段**：先写第三节那 5~8 条角色场景，每一步「这个人要填什么、要看到什么」列出来，并集就是字段表；场景里没出现的不加。
- **你不了解这家客户的真实业务——默认按「最小可用」设计**（2026-09-24 用户：「主要原因你不了解实际业务」）。
  真实团队建一条任务/Bug，多数时候只填**标题、描述、指派给谁、优先级**。多一个字段，每条记录都要多看一眼、多想一次；
  少一个可选字段，用户一句话就能加回来。所以**拿不准的字段不建**，写进 design.md「我替你做的假设」的「省略的可选字段」里。
- **参照产品的「新建」弹窗就是字段上限**（用户给的 Teambition 创建任务）：
  标题、执行者、开始/截止时间、所属项目、类型、状态、标签、备注（富文本）、优先级 —— 一屏填完。
  **Bug 管理更少：提 Bug 只要「标题 + 内容（Markdown）」两个字段**（2026-09-24 用户：「提 BUG，不需要太多字段，就一个标题，
  一个内容采用 markdown 即可」）。提交人用系统创建人；指派给、状态、解决方案这些**由按钮维护**（「指派」弹窗选人、
  「解决」弹窗选方案），新建时不出现；严重程度、优先级、截止日期默认不建、写进「省略的」。
- **精简字段 ≠ 精简掉「归属维度」**：记录「属于哪个项目/产品/客户/部门」这种分组维度，真实团队几乎必有（多个项目并行）。
  它的表**不能只写进「省略的」**，要么直接建（提 Bug 多一个「所属项目」下拉），要么放进「需要你定的」第 1~2 问。
  处理历史（谁在什么时候指派/解决/激活）同理：由流程自动写，不增加填写负担，默认建（2026-09-24 用户看单表 Bug 系统：
  「BUG 管理系统就一个表吗」→ 追加 项目 + 处理记录）。不要叠「模块 + 影响版本 + 关联需求 + 关联任务 + 来源用例 + 解决说明 + 激活次数 + 各种日期」
  （2026-09-24 用户看 20 个字段的 Bug 页：「作为 BUG 管理系统，不需要那么多字段」）。
- **关联宁少勿多**：一张单据只挂主链路上真正要选的上级（Bug→产品/版本，任务→项目/迭代），「顺手也关联一下」的不挂。
- **同义字段只留一个**：解决方案（字典）和解决说明（文本）、备注和说明、描述和详情，二选一。
- **流程维护的字段**（状态、次数、处理人/日期）要建就建，但由流程/按钮写，页面上设只读或新增时隐藏（`struct_cfg.OPT_FLAGS`），不让人手填。
- 协作/研发类单据**通常 6~10 个字段**，管钱管合同的单据 10~15 个；超过就回头看哪些是「拿不准、先加上」的，删。

下表是**常见字段的写法**（用到时照这个写），**不是每张表都要有**：

| 字段 | 写法 | 为什么 |
|---|---|---|
| 单据编号 | `编号`：前缀 + 4 位 + 含日期 | 标题/检索 |
| 名称/标题字段 | 每张表指定 `标题`，名字以「名称/标题/编号」结尾（别用「内容/描述/说明」结尾——会被推成多行文本） | 关联记录下拉显示的就是它；**标题不能是关联带出字段**。放款/收费/检查这类没有自然名称的流水单，用自动编号当标题即可 |
| 状态 | 应用字典，状态机见第 4 步 | 流程与看板都靠它 |
| 申请人/负责人 | `选择用户`，默认当前用户 | 审批取人、看板按人统计 |
| 所属部门 | `选择部门`，默认当前部门 | 同上 |
| 日期 | 申请日期/开始日期/截止日期 | 看板时间维度 |
| 附件、备注 | 名字即可推断 | — |
| 长文档字段 | 需求描述、验收标准、重现步骤、任务描述、用例步骤、方案说明这类**要排版/贴代码截图**的，`类型` 写 `Markdown`（研发类参照禅道默认如此）；备注/意见仍是多行文本 | 多行文本只能纯文本（2026-09-24 用户：「任务管理系统里面的需求应该使用 markdown 文本」） |

基础资料表只要：名称（标题）+ 编码 + 3~6 个业务属性 + 负责人。

### 3. 关联（本层最容易出错的地方，逐条过）

**每条关联都要落成 `links` 一行**，下面五项缺一不可：

| 项 | 默认 |
|---|---|
| 目标表 | 写**真实表名**，不是控件显示名 |
| 条数 | 单据 → 基础资料 = `单条`；单据 → 明细行 = `多条` |
| 显示 | 单条：`卡片`（选主数据用 `下拉` 也行）；多条明细：`表格` |
| 双向 | 单据 ↔ 明细、主链路上的父子单据：**`双向: true`**。基础资料只对**主链路**单据双向（客户↔合同、项目↔任务），辅助引用（担保合同→担保产品）单向 —— 全开双向会让一张基础表挂 4~7 个多条页签（2026-09-24 实测），表单冗长 |
| 显示字段 | **必须主动给**：多条表格 **≥4 列**、单条卡片 2~3 列（不给就只显示标题一列，用户会当成「没勾字段」） |

- **明细行 = 双向关联的独立工作表**，不是设计器子表；明细行上要有回指父单的单条关联。
- **多条侧指向独立下游单据的，写 `新增时隐藏: true`**（客户→担保申请、项目→任务、合同→代偿）：新建主数据时不出现
  空的「+ 添加记录」块，编辑/查看时照常显示（2026-09-24 用户反馈「新建客户为什么底部有担保申请添加按钮」）。
  指向**本单明细行**的（申报书→预算明细、工时填报→工时明细）不写——建单时就要填。见 `app-spec.md`「新增时隐藏」。
- **双向 = 两侧各写一行 `links`**（多条侧 + 单条侧），`双向: true` 标在其中**任一行**都行；只写一行时找不到回指控件，precheck 会拦。
- **带出**：单据选了主数据后要显示的属性（客户的联系人电话、项目的负责人）用 `带出`，
  **带出字段名 = 目标表里的真实字段名**。流程要在明细行上读的键（编码、父单号）也必须带出到明细行
  （流程在明细行上只能读本行字段，见 `app-prompt-skeleton.md` 第三节）。
- 父单上的合计 = `summaries`（关联字段 + 汇总列 + 方式），不要用公式去拼明细。
- **「取关联字段」默认值只给「照抄」类字段**（申请单的标准费率、客户的联系人）。**审批/评审结论类字段**（批准金额、批准费率、核定期限）不要配：服务端在接口新增时会强制覆盖传入值（engine-contract #17），评委定的数被申请值顶掉（2026-09-24 担保-一句话6 K4）。
- **被流程回写父单的子单据，必须带出父单编号**（桥字段）：流程在子单据上只能读本行，按「父单编号」`get_one` 定位父单，
  且 `get_one(..., sort="编号字段")` 写上排序字段。

### 4. 数值字段（审批条件、汇总、公式、看板指标都靠它）

**凡是金额、数量、工时、比例、分值，一律在 `forms[].类型` 里显式写「金额 / 数字 / 整数」**，
不要赌名字推断——`计划资金`、`拜访费用`、`担保额度` 这类名字推断曾落成单行文本，
于是「金额 ≥ 100 万走总经理审批」在比较一个文本、汇总在对文本求和，**所有闸门全绿、跑起来全错**。

- 单位不是「元」的（万元、%、小时、天）同时写 `选项.unitText`，建完回读 `unitText`。
- **比例/费率/百分比写 `选项.precision = 2`**：「数字」默认 0 位小数，1.5% 填不进去，闸门不报。
- **计数类汇总（记录数）在接口写入的数据上为空**（engine-contract #19）：照建，冒烟**不要断言它**，页面验收。
- `precheck.py` 会拦：被 **流程条件（大于/小于…）/ 求和类汇总 / 算术公式** 用到的字段不是数值类型 → 直接报错。
  报了就补 `类型`，**不要**改流程条件去迁就类型。

### 5. 状态机 + 流程（每条都要能说出「谁、什么时候、改了什么」）

每张业务单据先定状态机，写进应用字典，例：`草稿 → 审批中 → 已通过 → 已完成 / 已作废`。
「已驳回」用**审批结果分支**写：`approve("部门经理审批", …)` 后接 `approve_result(ok=[写已通过], reject=[写已驳回])`
（建后套件是 `result_branch()`；2026-09-24 起可用，以前只能不设或人工改）。冒烟两支都要测：approval 里 `'reject': ['部门经理审批']`。
**「查不到就结束」用 `get_one(empty="分支") + data_branch(found=[…], missing=[])`，别用 `empty="中止"`**：
中止会给发起人发一条「流程结束通知：查找结果无数据」，每触发一次收件箱多一条（项目申报-一句话10：第 2 位专家评审起每次都发）。
**同一个状态字段被多条流程写**时按状态机排先后：例「需求评审通过写已确认」会覆盖「任务联动写开发中」——
审批后的写回改成带条件（只在仍是「评审中」时写），或拆成两个字段（评审状态 / 开发状态）。

一句话需求的**默认流程套路**（按需取用，不要全堆）：

| 套路 | 触发 | 节点 |
|---|---|---|
| **金额分级审批**（只在业务本身有金额时用：采购/报销/合同/借款/担保/资助；研发、缺陷、任务类**不用**） | 单据新增 | 更新状态=审批中 → 网关：金额 `大于等于` 阈值走「上级领导/总经理」审批，其他情况走「部门负责人」审批 → 更新状态=已通过 |
| **状态流转 + 指派**（研发/缺陷/工单类的主套路） | 按钮 | 每个状态一组按钮（确认 / 指派 / 解决 / 验证通过 / 关闭 / 激活）→ 更新状态 + 当前处理人 + 时间戳（解决日期、关闭日期）；新增时给指派人发系统消息 |
| 明细回写 | 单据确认/审批通过 | 取本单明细 → 逐行调子流程 → 更新台账/父记录 |
| 关联状态联动 | 子单据新增/状态变更 | 取单条父记录 → 更新父记录状态/进度 |
| 按钮流转 | 自定义按钮 | 更新状态（提交/完成/作废/领取…） |
| 到期提醒 | 定时 | 取多条（截止日期 < 今天 且 未完成）→ 系统消息给负责人 |

- **设计审批前先跑 `scripts/tenant_probe.py --api-base … --token … --tenant-id <id>`**（只读）：一次列出角色+成员、部门树、用户所属/负责部门，并提示「没有负责人的部门」。不用再自己写探针。
- **审批人必须能在本租户解析到人**（2026-09-24 三个应用全踩：四道闸门全绿、任务谁都收不到）。设计前先查一次租户角色：
  `GET /sys/role/list?pageNo=1&pageSize=500`（带 `X-Tenant-Id`），从**现有角色**里选，写进 design.md 假设。
  · 高额 / 领导审批：`approve("总经理审批", roles=["<现有角色名或 roleCode>"])`（build_flows 自动解析成 roleCode，查不到直接报错）；
  · 低额 / 直属审批：`appr("部门负责人审批", who="部门负责人")`（发起人所在部门的负责人；**部门没设负责人时任务无人可办**，
    冒烟要看「进了待办」）；⛔ `who="上级部门负责人"` **别当默认**：上级部门没设负责人时实例照起、任务无人可办、
    不报错（2026-09-24 实测，契约闸门也拦不住——取决于运行时组织架构），只在确认上级部门有负责人时用；
  · 指定人：`approve(..., users=["登录账号"])`，账号必须存在。
  租户里没有「总经理」这类角色时，用最接近的现有角色并在假设里写明，**不要**编不存在的角色/账号。
  阈值取行业常见值并写进 `design.md` 的假设里（如「借款 ≥ 50 万需总经理审批」）。
- **选了角色就查成员**（`/sys/user/userRoleList` 或角色成员接口），确认冒烟用的账号在该角色里并写进假设——
  否则冒烟断言不了「进待办」，只能看落点。
- **同一张单据按结论分几种结果**（立项/不立项、通过/不通过）：写**一条流程 + 网关多分支**（不带条件的那支兜底），
  不要写两条同表同事件的流程（precheck 会提示，两条互相覆盖状态的风险要你自己推理）。
- 高额加签模板：`金额 ≥ 阈值` → 部门负责人初审 → 领导角色复审；其他 → 部门负责人审批。各审批节点**名字互不相同**，冒烟才能断言落点。
- **「算出来再判」别用运算节点 + 网关判 `result()`**（进销存-速测19/20 两轮、5 种写法都恒走默认支）：
  在表上加公式字段（如「未收款金额 = 应收 − 已收」），再 `get_one(表, cond=[(公式字段, "小于等于", 0), …], empty="分支")` + `data_branch`。
- 网关必须留一支不带条件的默认支；判据字段必须是**触发时就有值**的字段（中途才填的字段恒走默认支，见 `flow_dsl.gateway`）。
- 审批要写「同意 / 不同意」两种结果时，审批节点后接**审批结果分支**（`approve_result` / 建后套件 `result_branch`，
  2026-09-24 实测可用）；**不要**接「意见分支」（suggest，本机保存报错，见 r12 报告）。只需「通过后写状态」时直连即可。
- 有驳回就要能**重新提交**：审批只在「新增」时触发，被驳回的单据改完没法再走审批 → 加一个按钮流程「重新提交」
  （已驳回时显示：状态改回审批中 + 同一套审批），或在 design.md 写明「驳回后新建一张」（担保-一句话11 反向检查发现）。
- 流程写法、节点契约照 `fast-full-chain.md` 的「简流」节与 `miniflow/references/node-contract.md`，本页不重复。

### 6. 看板（1~2 张，每张 4~6 个图）

按「领导打开第一眼想看什么」选：各状态单据数（饼/柱）、金额（有金额的业务）或数量按月趋势（折线）、按部门/负责人排名（条形）、
本月关键指标（指标卡）。每个图写清：数据源表、维度、指标（数值指标必须落在第 4 步的数值字段上）。
宽度/布局规则见 `app-prompt-skeleton.md` 看板条目。

### 7. 菜单与按钮

- 分组按业务线：基础资料放最后；明细行表**导航隐藏**（规格表达不了，写在建后套件 `appconfig.py` 的 `HIDE_MENUS`）。
- **分节标题别和字段/关联控件同名**（「担保合同」分节里放「担保合同」列表 → 按名字引用有歧义，precheck 提示）：写「合同信息」「合同列表」这类。
- **分节（layouts）由你定**：一句话需求不存在「点名分隔符」，`app-spec.md`「没点名就不画分节标题」那条在本场景不适用——
  **每张表都写 `layouts`**：字段 ≥ 8 的单据给 2~4 个带标题的分节（基本信息 / 金额与期限 / 审批信息 / 附件），
  其余表写**一个标题为空串的分节**（只分卡不画线）。**不写 layouts 的表会一字段一张卡**、关联字段追加在多行文本之后
  （2026-09-24 第 2 轮：6 张小表返工）。在 design.md 写一句。
- 每张有状态机的单据给 1~3 个流转按钮（提交审批 / 标记完成 / 作废），按钮绑按钮触发的简流。
- 流程/按钮维护的字段（状态、次数、处理人与日期）设只读或新增时隐藏（见第 2 步），不让人在新建时手填。

## 二、`design.md` 格式（一屏，给人看）

```markdown
# <应用名> 设计方案（由一句话需求「……」补全）

## 分组与表
- 缺陷：Bug（标题：Bug 标题）、项目；[明细，导航隐藏] 处理记录

## 每张表的字段（为什么是这些）
- Bug：**提 Bug 只填 标题、所属项目（下拉）、内容（Markdown）**；按钮维护 指派给、状态、解决方案（新建时不出现）
  —— 提 Bug 的人只说「哪个项目、什么问题」；谁来修、怎么解决是后面的环节
- 项目：项目名称、负责人、状态；项目里看它的 Bug（新建项目时隐藏）
- 处理记录：所属 Bug、操作、操作人、说明、时间 —— 全部由流程自动写，没人手填

## 关键关联
Bug → 项目（单条下拉，双向：项目里看它的 Bug）；Bug ↔ 处理记录（多条，双向，流程写）

## 关键数值字段
无（研发类**没有金额字段**；严重程度、优先级是字典不是数字）

## 流程
1. Bug 流转按钮：开始处理 / 解决（填解决方案）/ 关闭 / 重新打开 → 改状态 + 指派给
2. 「指派」按钮 → 给被指派人发系统消息（新增时还没有指派人）；Bug 解决 → 给创建人发「待验证」消息

## 看板
缺陷总览：各状态 Bug 数、按严重程度分布、按处理人待办排行、每日新增/解决趋势

## 我替你做的假设（不对就直接说，改起来很快）
- Bug 状态：待处理 → 处理中 → 已解决 → 已关闭，可重新打开；不做审批
- **省略的可选字段**（要就说一声）：严重程度、优先级、截止日期、模块、影响版本、Bug 类型；需求/迭代/测试用例/版本 这几张表也先不建
- 未灌测试数据
```

## 三、交付前自检（除 `fast-full-chain.md` 的闸门外，本层额外五条）

1. **关联逐条回读**：每个关联控件的目标表、单/多条、显示方式、显示字段、双向，与 `design.md` 对照，不符 0。
2. **数值字段逐个回读**：`design.md`「关键数值字段」里每个都是 `money/number/integer`（或公式/汇总），单位对。
3. **主链路冒烟**（`smoke_flows.py`，配置写法见 `smoke-flows.md`，数据按记录 id 清理）：
   - 至少一条「主数据 → 单据 + 明细 → 流程回写」链；
   - 每条分级审批（有才测，**别为了测它去设计金额审批**）：金额低于/高于阈值各造一单，用例写 `'approval': {'node': '<该分支审批节点名>'}`，
     断言实例已起、状态已写成「审批中」、当前停在对应节点、**任务进了办理人待办**（任务无人收是本层最贵的静默故障）；
   - 清理：先清流程实例（`GET /act/processInstance/clear?processInstanceId=`，脚本自动做），再删记录，零残留。
4. **业务场景冒烟：这是不是客户要的系统**（闸门和流程冒烟只证明「建对了」，证明不了「建的是对的东西」——2026-09-24「类似禅道」四道闸门全绿、冒烟全过，交付的却是带预算审批的通用任务系统，用户一眼否掉）。
   - 先按参照产品 / 行业写 **5~8 条角色视角的业务场景**（谁、在哪张表、做什么、期望看到什么），写进 `design.md`「业务场景」节。
     例（禅道式）：「测试提 Bug 指派给开发 → 开发收到消息、在待处理里看到 → 解决并填解决方案 → 测试收到验证消息 → 验证关闭 / 不通过重新激活（激活次数 +1）」；
     「经理打开看板看各模块未关闭 Bug 数和本周新增/解决趋势」。
   - **每条场景在真机上走一遍**（能用 smoke_flows 的写成用例，`doc: (表, '@别名')` 串起同一条单据的多个按钮；
     看板/列表类回读数据核对），逐条记 通过 / 不通过 / 做不到（缺表、缺字段、缺按钮、状态走不到、看板答不了）。
   - 再过一遍**反向清单**：有没有参照产品里**不该有**的东西（研发类出现预算/金额审批、担保出现与业务无关的字段）；
     参照产品的**核心对象/核心流转**有没有漏（禅道：Bug 生命周期、指派、重新激活、解决方案、影响版本；担保：反担保、保后、代偿、追偿）。
   - 交付报告里单列「业务场景验收」：每条场景的结果 + 做不到的原因 + 建议补法。**有做不到的主场景不算交付**。
5. **字段过一遍用途**：每张单据逐个字段对照业务场景，说不出「谁在哪一步填/看、拿来做什么」的删掉；在 design.md 每张单据后写一句「为什么是这些字段」。
