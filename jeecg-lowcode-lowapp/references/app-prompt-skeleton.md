# 建应用提示词骨架（给写需求文档的人）

用本骨架描述一个新应用，规格作者就能**一次写对**、`precheck.py` 也能一次过。
2026-09-16 建 50+ 表应用实测：**整轮 42 分钟里有 15 分钟是需求/规格里可静态发现的
缺陷导致的重跑**。那些缺陷全部对应下面某一条。

---

## 一、必须写清楚的（缺一条就要在真机上返工）

| # | 要写什么 | 为什么 |
|---|---|---|
| 1 | **每个业务对象：管哪些信息**（字段的业务含义） | 字段名即语义 |
| 2 | **谁关联谁**：关联哪张表、`单条` 还是 `多条`、列表里显示 `卡片`/`下拉`/`表格` | spec_infer 猜不出来，必须显式 |
| 3 | **带出哪些字段**——写**目标表里的真实字段名** | 写「显示名」会落不下；带出字段名必须与目标表字面一致 |
| 4 | **汇总**：主表哪个字段 = 哪张明细表的哪一列求和 | 同上 |
| 5 | **自动编号**：前缀 / 位数 / 是否含日期 | 同上 |
| 6 | **计算规则**：写成公式，并**确认引用的字段在本表存在** | 占位符写错只在真机补丁阶段报 |
| 7 | **枚举**：作为**应用字典**给出（字典名 → 选项文案） | 表单里直接绑字典 |
| 8 | 每个表单的**标题**用哪个字段 | 标题是关联记录下拉的显示值 |
| 9 | 看板：答什么业务问题 + 数据源表 + 维度/指标 + 筛选维度 | 透视表**必须**有度量列（清单式给「记录数」） |
| 10 | 流程：触发时机（新增/修改）+ 节点 + 审批人 + 逐行处理谁 | 见第三节 |

## 二、**不要**写叶子控件类型

「设备名称=单行文本、合同金额=金额、安装地址=省市区」这类**不用写**：

- 写了会让规格从 ~19k token 涨到 ~32k token，**超过单次输出上限**，只能拆多次写 → **更慢**；
- 命名推断对叶子字段实测**严格 95.1% / 等价 100%**，剩余多是
  money↔number、input↔textarea 这种**外观差异**。

> ⚠️ **「真错 0 / 叶子类型没有一处导致返工」这个结论已被推翻**（2026-09-20 销售管理实测）。
> 确实会错，而且错了**不影响应用能不能跑**，只影响**跑出来对不对**：
> `合同金额` `合同税率` `销售合同名称` `合同相对方` 被推成**附件上传**（文件类关键词「合同」
> 当时是子串匹配），于是**对「合同金额」求和的汇总实际在对一个附件字段求和**——
> 建表、接口、契约检查全绿，只有人肉看汇总数字才发现。规则已改成后缀锚定（见 `app-spec.md`），
> 但**别假设推断一定对**：凡是名字里带「金额/税率/附件/合同/价」这类词、
> 或语义与字面不符的（`技术协议` 是附件、`客户重要程度` 是星级），建完**回读一遍控件类型**。

**例外**（名字推不出来的才写）：**多选**、**子表（可加多条）**、**图片/附件**、
以及「名字像文本其实是枚举」的字段（如「需求来源」「收款项」「付款方式」），
在需求里点一句「这几个是单选/多选，选项如下」即可。

**推断猜错时的补救（2026-09-20 起）：** 在规格里加 `"类型": {"字段名": "中文类型名"}` 逐条纠正
（**只写错的那几个**，不要全量写——token 成本的理由照旧）。在此之前规格**没有这个口子**，
猜错了只能建完表再用补丁脚本改控件。

> ⛔ **反过来的坑：名字推断本来推得对的，被「顺手补一句类型」补错了**（2026-09-22 实测）。
> 形如「XX**大写**」的字段名，`spec_infer` 的正确输出就是 `capital-money`；
> 作者在规格里顺手写了 `"XX大写": "金额"` —— 而 `类型` 是**显式声明、优先于名字推断**的，
> 于是正确结果被覆盖，落成普通金额框，表单上该显示大写金额的地方是个空输入框。
> **规则：只写推断会错的那几个；凡是靠名字能推对的（尤其带「大写/附件/图片/日期/金额」这类
> 关键词的），一个字都不要写。** 要写就必须用 `spec_infer.TYPE_CN` 的词表：
> `大写金额`（不是「金额大写」）/ `选择用户`（不是「选人」）/ `附件上传` / `静态下拉` …
> —— **词表不同名 = 每次都要人肉翻译 = 早晚抄错**。

**「默认值：取[X]的「Y」」和「他表字段」是两档，别混写**（2026-09-22 实测）：

| 需求写法 | 落库形态 |
|---|---|
| 「金额 / 单行文本，**默认值**：取「X」的「Y」」 | 普通控件 + 默认值（建时 copy 一次） |
| 「**他表字段**，取「X」的「Y」」 | `link-field`（跟着关联记录走） |

两档在规格里对应**不同**的声明位：前者靠 `类型` + 默认值配置，后者必须写进 `links` 的 `带出`
—— 而 `带出` 会把同名项从 `类型` 里摘掉。**把默认值那档写成 `带出` 的后果**：控件变成链接字段、
默认值静默失效，四道闸门全绿，只有人肉点开表单才看得出（2026-09-22 实测：一张应用里 7 个字段）。

**「默认值：自动计算 X」随字段类型变义，写需求时按类型分开表述**：
落在**数字/金额**上 ＝ **公式控件**（实现细则把「单价 × 数量」这类定死为公式，**不是汇总**）；
落在**日期**上 ＝ **默认值（函数计算）**，控件仍是 `date`（例：「周截止日期 ＝ 周开始日期 ＋ 6 天」）。
同一种写法两种落库形态 —— 按「自动计算」一律当成公式控件去做需求↔实机对账，会在日期字段上误报。

## 三、流程可达性契约（**照抄这一节**）

流程跑在**明细行**上，而明细行**只能读自己这一行的字段**——取不到父单据的值。
所以凡是被流程逐行处理的明细表，**必须物理携带**它那条流程要读的键。
清单靠推导：**把每条流程 `ref()` / `cond` 里用到的字段列出来，逐个核对明细表有没有**，
缺的用「关联 + 带出」补上。按用途分通常是这四类（字段名以你的表为准）：

| 用途 | 典型字段 | 怎么来 |
|---|---|---|
| 复制上游关联 | 上游实体（关联记录本身） | 关联该实体时带出 |
| 上游冗余 | 上游实体的名称 / 编码等 | 同上 |
| 回写父单据 | 父单据号 | 再建一条**指回父单据**的关联，带出 |
| 定位 | `cond` 里用来定位本行的字段 | 同上 |

配套三条（写需求时就要确认）：
1. **定位键 = 你在 `cond` 里用来唯一区分一行的那几个字段**；
   「没有就新建」之后必须把定位键一起写进去。
2. **流程里做不了算术**：累加/扣减用 `inc()/dec()`；「合计 / 余额 / 当前可用」
   这类派生量定义成**工作表公式字段**，流程只写基础计数。
3. **跨表回写靠两侧同名同值字段**做匹配（桥字段两张表都要有、且同名）。

## 三·补、写流程型应用时必须额外写死的（2026-09-20 进销存实测归总）

在这十条之外，凡是**要跑流程改数据**的应用，需求文档还必须点名：

| # | 要写什么 | 为什么 |
|---|---|---|
| 11 | **他表字段一律「存储数据」**（`saveType=save`），点名"仅显示"的除外 | 仅显示 = 不落库；流程拿它当定位键时恒取空值 |
| 12 | **双向关联成对声明**：哪两张表、哪两个字段互指 | 只写一侧 = 明细挂不上单据 |
| 13 | **凡是流程要用到的表，都要有 `仓库编码` + `产品编码`（存储数据）** | 流程按这两个编码定位库存行，两个都要匹配（AND） |
| 14 | **明细表要带「指向对方明细行」的关联记录**（如出库明细→销售产品明细） | 数量回写要靠它找到该加/该减的是哪一行 |
| 15 | **流程里写字典字段要用「落库 value」**（value 通常 ≠ label，建完字典要回读） | 写 label → 条件不成立 + 表单回显为空 |
| 16 | **两个选项的字段用单选/多选组**（是/否 类），三选项以上才用下拉 | 只有两项时下拉要多点一次 |
| 17 | **每个仪表盘第一行放一个整行标题文本组件**（字号 28 / 居中 / 内容是用途描述） | 盘面无标题看不出用途 |
| 18 | **同一排组件必须等高、宽度只用 6/8/12/24** | 非标准宽度会左右错位 |
| 19 | **不要给表单已有的金额/数值字段再配"计算值"** | 表单里已是汇总/公式，图上直接绑 |
| 20 | **关联记录「表格」模式至少 4 个显示字段** | 只显示标题一列时明细区形同虚设 |
| 21 | **每道审批写明「审批人是谁 + 通过写回哪些字段 + 驳回写回哪些字段」** | 审批节点本身不改数据，写回全靠这两条分支；不写就点了通过库里还是旧值。审批人默认 = 发起人自审 |
| 22 | **需求里列的选项文案是 label**；在意落库值就写清 value（如「`1 跟进中`」= value `1` / label `跟进中`） | 表单与流程存的是 value，拿 label 去比/去写 = 条件不成立 + 回显为空 |
| 23 | **凡是「按某张表的记录定位、没有就新建」的流程**（记账/台账/结存类），点名要**显式判「查到没有」两条支路**：查到 → 只更新计数；没查到 → 一次把整行建对 | 靠引擎「没查到就自动建」时，建出来的行只有更新节点里那几个字段 —— 关联记录这类**只能一次带全**的字段补不回来 |
| 24 | **要往台账/统计表写的「关联记录」字段**（仓库、产品、客户…），点名要求**上游明细表挂一个隐藏的中转字段**，默认值 = 顺着本表指向父单据的关联记录取值 | 明细行上只有「XX编码/XX名称」这类**纯文本**带出字段，**不带指针**，写不进关联记录列 |

> **23/24 的判据**：需求里出现「库存/余额/台账/累计」这类**派生表**，且它按
> 「某实体 + 某实体」一行的粒度聚合 —— 就属于这一档。对应规格的
> `get_one(empty="分支") + data_branch(...)` 与 `中转字段`。
> 全案见 `engine-contract.md` 第五节「台账类回写」。

## 四、交付前必做

```bash
# 1) 零真机预检（纯静态、不联网）—— 不过就不要动真机
python "<lowapp>/scripts/precheck.py" --spec app_spec.json --flows flows.py \
    --expect "分组=7,表单=52,字典=22,看板=25"   # 按当轮规格实际数字填

# 2) 真机建
python "<lowapp>/scripts/build_app.py" --api-base URL --token TOK \
    --tenant-name 租户 --app-name 应用 --create-app --spec app_spec.json --rows 0

# 3) 流程（改了 flows.py 要加 --update，否则同名静默跳过）
python "<miniflow>/scripts/build_flows.py" --api-base URL --token TOK \
    --tenant-id N --app-id A --spec flows.py [--update]
```

**回读核对**：分组/表单/看板按菜单 `type` 计数、字典按 `getDictListByLowAppId`、
流程按 `openStatus` + `processStatus` 均 1 过滤、看板按 `/drag/page/queryById` 的
`template` 组件数。**有缺口必须报出来，不要静默通过。**

## 五、**成组出现的需求**要按原文逐条点名核对（2026-09-20 销售管理实测返工）

需求文档里有一类句子会**换个字段名重复出现十几次**（「默认取关联记录「X」的「Y」」、
「默认当前用户所属部门」、「从关联记录带出 X · Y 存储数据」…）。
首轮按印象铺这类需求，**漏掉的几条在界面上完全看不出来** —— save 全绿、回读也查不出
（因为压根没有那一行配置可查），只有用户点到那个字段才发现。

实测：销售管理的「默认取关联记录「X」的「Y」」共 **11 条**，首轮只铺了 8 条，
漏了 `拜访记录.目标客户` / `回款记录.机会目录` / `机会目录联系人.目标客户`
（用户就是点开拜访记录时发现的）。**收尾自查要按需求原文逐条过一遍**，做法：

```python
# 从需求原文抽出所有同句式条目 → 与实现表逐条比对，缺的直接打印
# （本次自查口径：真·默认值需求 43 条，未落实 0 条才算过）
```
**「有配置可查」的用回读断言，「压根没那一行」的只能靠需求原文点名核对** —— 后者是这类
静默遗漏的唯一防线。

⚠️ **连带一个坑：需求里的「关联记录「X」」写的是**工作表名**，不等于控件名。**
`机会目录联系人` 表上指向机会目录的控件叫**「所属机会」**，照抄表名当控件名去查 →
查不到、整条静默跳过（本次靠 applier 的 `MISS … (控件=True 关联=False)` 报了出来）。
**落库前先按名字核实那个控件在本表存在**，别信需求里的指代。
落库形态见 `desform-default-value.md`「字段引用」——`$<关联记录控件的 key>.字段model$`，
**前缀是控件 `key` 不是 `model`**（写错设计器显示「字段已删除」）。
