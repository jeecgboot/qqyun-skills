## ⑨ 规格必须自带精确命名表（2026-09-16 实测）

**前提认知，先记住：需求文档通常就是一段业务描述，没有可对照的现成应用。**
所以规格里的「字段名 / 关联名 / 带出名 / 子表列名 / 标题」**必须在文档里写死**，
不能指望执行者去别处比对、更不能靠业务直觉推。

历轮翻车**全部**出在这里：把 `选择设备` 写成 `设备`、`责任部门名称` 写成 `部门名`、
`含税金额/元` 写成 `含税金额`、子表列名靠猜。**每一个名字都是一次返工。**

> ⚠️ **2026-09-24 澄清**：上面最后一例（`含税金额/元` → `含税金额`）**就是写错了名字**，
> 正确做法是**把 `含税金额/元` 原样写进规格**。不要理解成「规格只能写短名、靠 RENAME 补后缀」——
> 那是 2026-09-16 曾在本仓库立过、**已于 2026-09-24 作废**的一条假规矩
> （`app-spec.md`「四条硬规矩」第 1 条、`app-prompt-skeleton.md` 第 25/26 条有完整溯源）。

**命名表怎么来：用户直接给命名清单时，原样写进规格并声明它是唯一权威**
（业务描述与它冲突时以它为准）；正文里的字段罗列**删掉**——两处都写、两处不一致，
就是返工的源头。

**带出字段名要写「目标表上的真实字段名」，不能写本表显示名。**
带出控件的 `name`（本表显示名）与它引用的源字段名**允许不同**（重名时平台会迫使改名），
规格里声明带出时必须用**后者**。只记本地名 → 目标表上没这个字段 → 预检/补丁全红。

> ⚠️ **`带出` 只能同名校对。** `带出` 是**纯字符串数组**，元素只能是目标表上的真实字段名；
> 落地的控件名 = 源字段名。想用别的本地名 —— **用 `带出映射`**（见下），不要走下面那些弯路。
>
> 2026-09-17 曾试过把映射关系**塞进 `带出` 数组本身**，写法全部失败/无效：
> `"a->b"`、`"a:b"`、`"a=b"`、`{"字段":..,"本地名":..}`、`{"name":..,"field":..}`、`["a","b"]` 二元组。
> **失败根因是找错了键位** —— `带出` 数组里只能是纯字符串。**另开一个 `带出映射` 键即可**
> （2026-09-24 真机实测通过，见下），当时为此白跑了 4 轮语法试错。
>
> ### ✅ 第三条路：`带出映射`（2026-09-24 真机实测，**首选**）
>
> ```json
> {"表": "报价单", "字段": "选择客户", "目标": "客户", "条数": "单条", "显示": "卡片",
>  "带出": ["客户名称", "客户编码", "销售负责人"],
>  "带出映射": {"客户联系人姓名": "联系人名称", "客户联系人手机": "联系人手机"}}
> ```
> **键 = 本表控件名，值 = 源表上的真实字段名。**
> 实测落 `link-field` + `saveType=save`，`showField` 精确指向源表字段 ——
> **两侧名字毫无共同前缀也照常命中**。`build_app`（建壳）/ `patch_fields`（补丁）/
> `app_audit` / `precheck` 四处都认这个键。
>
> **它取代了下面那两条路**（那两条只在 `带出映射` 不够用的极端场景才考虑）：
> 1. ~~改源表字段名~~ —— 会把污染扩散到**所有**引用该表的表（`客户.联系人名称` 改成
>    `客户联系人姓名` 之后，供应商侧也得跟着改，而两侧要的名字**不一样**）；
> 2. ~~建完整单设计补丁改 `name`~~ —— 该字段已存在会撞名，得先 `delete_widget` 再改名，
>    而 `delete_widget` 会换 `model`、打断引用它的他表 `showField`，代价很高，一般不划算。
>
> ⛔ **历史教训**：进销存那个 47 表应用曾用**建后 `RENAME` 改名表**（`{表: {旧名: 新名}}`）
> 来实现同一件事 —— 233 条改名牵动 47 张表，其中 **38 张是纯被改名拖进来的**，
> 还把规格名与真机名劈成两套（流程/看板写错名字时**四道闸门全绿**）。
> **`带出映射` 能做的，不要再上 `RENAME`。**

写规格时的判定规则（每条带出都要落在前两档，剩下的逐条标出来）：

| 档 | 判定 | 文档里怎么写 |
|---|---|---|
| A | 目标表上确有同名字段 | 直接写名字 |
| B | 目标表上有这个字段，但名字不同 | `目标表字段名（本地 本地名）` —— **规格写前面的** |
| C | 目标表上找不到 | 标 `⚠`，**在「已知缺陷」节里指定正确字段名**，不能只标不指 |

C 档常见于「复制粘贴建的表」：关联还指着复制前的表，名字也对不上。
**C 档必须在文档里给出替换名**，并顺手核一遍替换名在目标表上真实存在 ——
否则等于把坏绑定换个写法继续传下去。

> `.strip()` 顺手做一遍：名字**首尾**的空白（前导空格、尾部 TAB）在 JSON / 脚本 /
> 预检之间极易被吃掉，留着必然对不上。只去最外层。

## 建库时必踩的四个坑

- **表 code 每轮重新生成**（形如 `t13a7cNN`，NN 恒等于规格里的序号，前缀是当轮
  按「应用名 + appId」算出的哈希）。看板声明若沿用**上一轮**的 code：
  `build_dashboards.py --dry-run` **仍能规划出全部页面**（它不按字面 code 解析），
  所以这不是「必坏」；但**建盘前按表名重映射一次**能把行为钉死
  （表名 →(上一轮 code 表)反查 → 新应用菜单取新 code）。
- **`build_app.py --rows` 默认 `0` = 不灌测试数据**，这就是**默认行为**：
  只有用户提示词**明确要求**灌数时才传 N。不传时灌数段**整段跳过、不做任何读**。
  （显式传 `--rows 0` 与不传等价。）
- **首页按钮分两批，来源不同**：spec 的 `buttons` 块只声明「打开列表视图」按钮
  （建盘脚本会建）；**「跳转到各张看板」那批要另加** ——
  `qqy_ops.py add-buttons --specs-file <json>`，pageId **必须从新应用的菜单取**
  （`drag` 行的 **`menuUrl`** 列，不是 `id`）。加完回读页面的 `config.chartData`
  数按钮个数。

  > **2026-09-17 起这条已收进 `build_dashboards.py`**：它改成**两趟**——
  > 先把所有盘建完，再统一加按钮。于是 `"page": "<看板名>"` 这种写法在 spec 里
  > 直接可用，不必再手写 pageId、也不必把「首页」排到它要跳转的看板后面。
  > 老版本一趟建成时，「首页」排在前面 → 目标盘的 pageId 还不存在 →
  > `[btn] 找不到看板 xxx`、按钮 `customPage` 为空，**而盘本身照报 `OK:`**（静默半坏）。
  > 跳过已存在的盘时会先查一下盘上有没有按钮组件，没有才补 —— 重跑不会叠加按钮组。
- **标题可以是他表字段 / 关联记录**：构建器解析不了这种标题，会**静默回退**成别的字段
  （实测：某表标题落成了它自己的编号字段，规格要的是上游的 `设备名称`）。
  所以规格里凡是「标题是他表字段/关联记录」的表，**建完必须逐表回读
  `config.titleField` 核对**；不符就手改：
  `design.config.titleField = <该控件 model>` → `save_design_from_file` → 再回读。

## 门禁的四个口径盲区（2026-09-28 项目管理 24 表实测）

交付闸门报的违例里，有几类**改不掉、也不该改**——它们是门禁的口径问题，不是交付缺陷。
认出来就别再花轮次去「消红」，直接把证据写进交付说明。

- **规格 `pages[].charts` 的键写「表名」，不要写编码**：`build_dashboards.py`
  编码/表名都收（按「是否含中文」自动切 `--form-code`/`--form-name`），
  但 `precheck` **只按表名解析** —— 写编码会被判「看板『X』引用了不存在的表 t4d5c30N」，
  而看板明明建出来了。表名两边都过。

- **`app_audit` 的「图表数」只数 `charts`，完全不数 `ui`**：只含 UI 组件
  （富文本 / 文本）的页面**恒报**「图表数 1 / 规格 0」。把 `ui[].comp` 从 `富文本`
  改成 `JDragEditor` 也一样（两条路径都试过）。这类页只能另外回读验收
  （`comp_ops list` 看组件在位 + 坐标尺寸），属门禁盲区。

- **一张表里不能有同名控件**：关联记录与汇总撞名时（如项目预算上
  「汇总 `人力成本预算`」+「关联记录 `人力成本预算`」），`app_audit` 报
  **「控件缺失」** —— 它按名字找控件，找到的是汇总那条，于是认为声明的控件不存在。
  改**关联记录侧**的名字即可；**汇总的 `options.linkTable` 绑的是控件 `key`、不是 `name`**，
  改名不影响汇总（`key` 没动）。走整单 `save_design_from_file`。

- **规格方言没有「文本组合」这个类型名**：`类型` 只收 19 个**叶子**类型
  （见 `app-spec.md`「`类型`」节），写「文本组合」`precheck` **直接报错**；
  撤回声明也躲不掉（`infer` 兜底成单行文本）。于是真机是 `text-compose`
  而规格声明不了时，`app_audit` 恒报「表 X.字段 声明 input → 实际 text-compose」。
  这是**方言缺口**：别为了消掉它把控件改回 `input`。

## 两条落库口径（同日实测）

- **`set-chart-filter` 是覆盖、不是追加**：对**已有一条**图内条件的图再跑一次，
  旧条件被顶掉（实测「待完成里程碑任务」先写了 `里程碑=Y`，再写 `任务状态≠已完成`
  后前者丢失）。多条件只能在已有那条的基础上直补 `config.filter.conditionFields`
  ——复制同表另一条条件的**整个对象**，`condition` 码 `1==` `2!=` `3>` `4<` `5>=` `6<=`，
  然后 `bi_utils.save_page(pageId)`。
- **`text-compose` 能吃 `required`**：需求把自动组合出来的「摘要」标成必填时，
  直接给它的 `options.required=True` 即可，能落库并回读为 `True`
  （必填语义不限于输入框）。

## 跨表引用的 model 会在「重建控件」后失效（2026-09-28 项目管理实测）

**症状 1**：面板上某个汇总/统计字段**永远空着**，别处数字都对。
**症状 2**：关联记录卡片上**少一列**（要求 4 列只画 3 列），且不报任何错。

**根因同一个**：建后补丁若把一个控件**原地换掉**（如把 `money` 占位换成 `summary` 真控件），
它的 `model` 会变成新的；而**别的表里指向它的引用不会跟着变** —— 汇总控件的
`options.field`（汇总列）、关联记录控件的 `options.showFields` 都存的是 **model 字面量**。

两个症状是**同一处悬空引用**：`项目.累计外采成本.field` 和 `项目.项目外采.showFields[i]`
都还指着改造前的 `money_…883012`，而真控件是 `summary_…760611`。
（对照：同一批次里 `累计工时成本`/`累计报销费用` 的引用没被动过，所以照常有值 ——
**别被"别处都正常"骗了**，逐条比才知道哪个是悬空的。）

**自查脚本思路**（跨表比对，门禁不会报）：
逐表建 `model → 控件` 字典 → 对每个 summary 控件，顺着 `options.linkTable`（= 关联控件的 **key**）
找到关联控件、取其 `options.sourceCode`（**目标表 code 在 sourceCode，不在 linkTable**！）
→ 断言 `field` 在该表的 model 字典里；对每个 link-record 控件断言 `showFields` 每一项都在目标表里。

> ⚠️ 设计子表来源的汇总例外：此时 `options.linkTable` 写的是**子表的 model**，
> 不是某个控件的 key —— 按 key 查会误报「找不到对应控件」，那是假阳性。

## 同名控件是原设计，别为过门禁改名（2026-09-28 项目管理实测）

项目预算上「**汇总 `人力成本预算`**」与「**关联记录 `人力成本预算`**」在需求文本和源应用里
**就是同名成对出现**（`项目外采预算`/`其他费用预算` 同理）。为消掉 `app_audit`
的「控件缺失」而给关联记录加「明细」后缀，是**偏离需求**的改法（2026-09-28 返工）。

- 那个「控件缺失」是**门禁口径问题**：它按名字找控件，找到的是汇总那条。
- 把 `app_spec.json` 的 `字段` 也按需求写成同名重复项后，**`precheck` 照常通过**
  （重复名不是错），`app_audit` 也不再报 —— 门禁与需求一致时就都干净了。
- 判据：**需求/源应用怎么写就怎么建**，门禁报的红先判断是不是口径问题，再决定动不动手。

## 日期控件写系统变量要用 `millisecond`（2026-09-28 实测）

流程更新节点往 **日期控件** 写「当前时间」时，`val` 写
`{"formNodeType":"system","variableValue":"millisecond","variableName":"毫秒"}`
（+ `valueType:3` + `valType:"variable"`），**不能写 `nowDate`/`nowTime`** ——
引擎把这两个一律格式化成 `'yyyy-MM-dd HH:mm:ss'` 字符串写库，而日期控件存的是**毫秒**，
同一列混两种格式。
`check_node_contract` 会抓这一条（"改用 millisecond"）；写**文本**字段仍是 `nowDate`。

## 手写追加流程节点：键集必须照抄一个已生效的同类型节点（2026-09-28 实测）

给已有流程追加节点时，只写「语义上必要」的键会 `saveFlow` 报 **500**
且信息量为零：`Cannot invoke "String.indexOf(String)" because the return value of
"…ChildNode.XXX" is null` —— **报的不是你缺的那个键名**，只能靠比对找出来。

实测缺的是 `pid`（= **上一个节点的 id**，首个节点写 `start`）和
`attr.expressionValue`（`${updateRecordDelegate}`）；顺带还缺
`attr.formType=2` / `formTableCode` / `formTableName` / `formTableId=form_start_<code>` /
`status:-1` / `addable:true` / `deletable:false` / `error:false` / `content:'工作表 "X"'`。

做法：**从本应用里挑一个同类型、已生效的节点，整份 deepcopy 过来再改字段值** ——
别凭文档拼。`data_update` 节点可能在 `conditionNodes[].childNode` 分支里，
`pj['childNode']` 一级链上找不到，要递归找。

回读验算：`childNode` 链能走到新节点、`attr.updateFields[0]` 的 field/val 对得上。
**但配置落盘 ≠ 行为生效** —— 必须再跑一次 `smoke_flows.py` 点那个按钮，
断言目标字段真的变了（本次靠它才确认「关闭问题」确实把状态改成了「已处理」）。

## 高级默认值里带函数必须写 `type: "function"`，不能写 `compose`（2026-09-28 实测）

`advancedSetting.defaultValue` 的 `type` 是个**语义开关**，写错不报错、只在页面上露馅：

- `compose` —— **只做 `$model$` 文本替换**，不做函数求值。
- `function` —— 走内置函数库求值（`CONCAT`/`IF`/`SUM`/`DATEADD`…）。

实测：项目.项目名称 要「[项目合同.合同名称] ＋ "项目"」，写成
`{type:"compose", value:"CONCAT($<合同key>.<合同名称model>$,'项目')", allowFunc:true}`
—— `$…$` **替换成功了**（合同名确实代进去了），但 `CONCAT` 不求值，
字段里渲染出**字面文本** `CONCAT(低代码产品,'项目')`。
`allowFunc:true` 救不了，那是**另一个 type 下的开关**。改成 `type:"function"` + `format:"string"` 才对。

> 判据：`value` 里出现 `函数名(` 且 type 是 `compose` → 写错了。
> 扫法（脚本里扫这两个键）：`re.compile(r'(?<![A-Za-z$])([A-Z]{2,})\s*\(')` 命中即改。
> 纯取值（如 `"$<关联key>.<model>$"`）用 `compose` 是对的，**别一起改成 function**。
> 同一轮扫「裸 model 漏写 `$…$`」时 0 命中——两者是不同的坑，别混。

## 「日期相减」不能用 CUSTOM 减法（2026-09-28 实测）

`mode: "CUSTOM"` + 表达式 `$结束日期$-$开始日期$` 看着对，**前端算出来的原始值是两个
日期时间戳之差 = 毫秒**：2026-09-21 → 2026-09-30 显示成 **`777600000`**
（= 9 天 × 86400000），字段名却叫「预计时长 / 计划耗时 / 距离截止日期天数」。
数值本身没错，**单位错**，而且不会有任何报错。

日期类时长一律走平台原生的日期模式（`formula` 控件自带，设计器面板也认）：

| 要算 | mode | 参数 |
|---|---|---|
| 两个日期之差 | `DATEIF` | `dateBegin` / `dateEnd` 都必填 |
| 距今天还有多久（未来为正） | `NOW_DATEIF` | `dateBegin` 必填，结束日固定为当前时间 |
| 已过去多久（工龄/账龄） | `PAST_NOW_DATEIF` | `dateBegin` 必填 |

- ⛔ **`options.type` 必须同时改成 `"date"`**（`desform-formula-function.md`「日期计算详解」写了这条，
  但**没说漏了会怎样**）：保持 `type:"number"` 时前端按数值格式化日期差 → **字段渲染成空白**
  （2026-09-28 实测：预计时长 从「777600000」变成「—」）。`mode`/`dateBegin` 全对也没用，
  回读配置一切正常，只有人看页面才发现。
- 一并照抄源应用（租户 1012「项目管理--第八版」，只读）：`unitText:"天"`、`decimal:2`、
  `expression:""`（该模式下留空是对的）、`datePrintFormat:"YYYY-MM-DD"`。
- ⛔ **`dateBegin` 是「开始」、`dateEnd` 是「结束」，别从旧的减法表达式里正则取值**：
  改造之前若字段是 `mode:CUSTOM` 的 `$结束$-$开始$`，**第一个引用是「结束」日期** ——
  照搬进 `dateBegin` 就接反了。实测症状：09-28 ~ 09-30 显示 **`-1天`**
  （`dateEnd − dateBegin` = −2，method=2 再 +1 = −1），不是空白、也不报错，很容易被当成「档位选错」。
  正确做法：**按字段名查出 model 再填**（`{x['name']: x['model']}`），不要解析表达式。
- `dateBegin`/`dateEnd` **必须写 `$model$` 包裹形态**（如 `"$date_179…$"`）。
- `datePrintUnit`：`Y`年 / `M`月 / `d`天 / `h`小时 / `m`分钟 —— 结果**带单位文本**（`9天`）。
- `dateFormatMethod`：`1` = 不含结束日当天（9-21→9-30 得 9天）；`2` = 含结束日当天（得 10天，
  请假天数那类用法）。**这一档要按需求语义选，别默认抄文档示例的 2**。
- 切到日期模式后 `expression` 置空（该模式下不读它，留着是死配置）。
- ⚠️ **改了没法在接口侧验算**：公式值服务端只存 `0.0` 占位（实测 `desformData` 里
  `formula_*` 恒为 `0.0`），日期模式的字段**根本不落库** —— 计算在前端做。
  所以只能靠浏览器刷新后肉眼看，`get_data` / `list_data` 都验不出来，别把它们返回 0
  当成「公式没生效」。
