## 一、简流（最高频踩坑区）

**1. 子流程的上下文只能读「本行」字段。**
`subflow(context="出库产品明细")` 里所有 `ref()`、`cond` 都只在本行解析，
**取不到父单据的值**（引擎两侧同名取值，跨表拿不到）。
→ 被流程逐行处理的**明细表，必须物理携带**它需要的键（第五节给推导方法）。

**2. 累加/扣减要用 `optType`，不能用 `calc()`。**
`flow_dsl.calc()` 是 `raise NotImplementedError`（引擎侧从不回填）。
`data_update` 的每个 `updateFields` 项支持 `optType`：`"1"`=设值 / `"2"`=增加 / `"3"`=减少，
**逐字段独立**——同一节点里「键字段设值 + 计数累加」可以混着写。
用正式 API：`upd_inc()/upd_dec()`（见 `flow_dsl.py`）。

**3. 派生量走工作表公式，流程只累加基础计数。**
流程里做不了算术，所以「合计/余额/当前可用」这类派生量定义为公式字段，
流程只写驱动它们的那几个**基础计数**。

**4. 「没有就新建，再更新」用 `get_one(..., empty="新增")`。**
新建出来的记录是**空的**，所以紧跟的 `update` 必须**把定位键一起写进去**
（即你在 `cond` 里用来唯一区分一行的那几个字段），否则下次还是定位不到、无限新建。

> ⚠️ **台账/库存这类表别用这一档，改用显式分支**（2026-09-21 用户实测后归口，见第五节）。
> `empty="新增"` 建出来的行**只有 update 里那几个字段**；而「关联记录」写不进 update，
> 于是自动建出来的行永远是残的。台账类一律 `empty="分支"` + `data_branch(found=, missing=)`。

**5. 回写类流程靠「两侧同名同值字段」做 cond。**
`get_one(目标表, cond=[X])` 要求 **X 在上下文表和目标表里都存在且同名**。
跨表回写拿不到单号时，用**两侧都有的业务字段**当桥——桥字段选谁取决于你的表结构，
但必须保证两张表里都有它、且同名同值。

**5-b. 流程里写的值必须是**表单真实存储值**，不是页面显示名。**
提示词说「【入库确认】等于『是』」，**「是」是业务语义，不是存储值** ——
字典生成的选项是 `[{label:"是", value:"0"}, {label:"否", value:"1"}]`（value 是**下标**）。
写显示名的后果：
· **条件恒不成立** —— 引擎拿 `"是"` 去 Mongo 里比 `"0"`，日志
  「匹配不到数据，不满足触发条件！」，**流程静默不触发**（2026-09-21 用户实测报障）。
· **写字段写空** —— 把「是」塞进 `updateFields[].val` / `formModel`，页面上该字段是空的。

**四处都要翻**，少一处就是半坏：主流程 `flow(cond=)`、网关 `gateway(branches=[{cond}])`
（⚠️ 它**另起炉灶**拼 queryItem、不走 `_cond_items`，实测最容易漏）、
写入（`update()` 的 `updateFields` / `add()` 的 `formModel`）、
**调子流程传参**（`call_sub(pass_={"账向": "应收"})` → 子流程里 `var("账向")` 写进字典字段：
`build_flows` 现按子流程里该参数写入的目标字段翻成存储值；2026-09-22 进销存实测此前落成文案，`app_audit` 也不查
`attr.variableList`，两边全绿）。同批补上：**部门控件写部门名** → 翻成 `[部门id]`（条件侧早翻了、写入侧漏了，
下游按部门判断的流程恒不命中，2026-09-22 销售管理实测）。

`build_flows.Resolver.field_value()` 已按此收编：字面量落库前翻成存储值，**认不出就报错**。
真值只有一处来源——表单设计里选项的 `value`；⚠️ `fetch_form_fields` 的 `options` 是
**裸值数组**（标签已被剥掉），要 label→value 对照只能回读 `/desform/queryByCode`。
验收走 `app_audit.py` 的 `[流程里的取值（真机回读）]`（本例 478 处全过）。
全案见 miniflow `gotchas.md` #105。

**6. 审批人=发起人。**
`approverGroups[0]` 用 `assigneeType="assigneeByExp"` + `expressionsIds=["${applyUserId}"]`
+ `expressionsNames=["获取发起人"]`。用正式 API `appr(name)`，不要手拼。

**7. `build_flows.py` 同名流程会「跳过」。**
改了 `flows.py` 重新跑**不会更新已建的流程**，只会打 `OK:skip`。
要生效必须 `--update`（重存+重发布，**保留原 processKey** —— 主流程的 `call_sub`
是按 key 引用子流程的，换 key 会断链）。

> ⚠️ **历史坑（已由 API 收编，但要知道成因）**：早期要在 `flows.py` 里自己 monkeypatch
> `Builder`，而 `build_flows.py` 是当脚本跑的、模块名是 `__main__`——
> 写 `import build_flows` 会拿到**第二份模块副本**，补丁打在副本上，
> 真正在跑的 `__main__.Builder` 纹丝不动。**save/deploy 全绿，配置全丢。**
> 现在 `$inc/$dec` 与 `_exp` 已是引擎原生支持，正常用不会碰到这条。

> ⚠️ **只重建子流程会打断它的「数据源」契约**（2026-09-21 实测）：子流程的
> `formTableList[0].isSubStart`、输入行登记名、节点引用，是**父流程那一趟回填的**
> （build_flows 的第 ③ 趟，注释原文「必须在父流程发布**之后**跑」）。
> 只 `--update --only <子流程名>` 时父流程没重存，回填不跑 →
> 6 条子流程当场报「formTableList[0] 无 isSubStart，子流程页数据源为空」。
> **改子流程后，必须把它挂的父流程一并 `--update`**（`--only` 会把引用的子流程自动带上，
> 直接点名父流程即可）。改完跑 `check_node_contract.py` 确认违例 0。
> 全案见 miniflow `gotchas.md` #107。

## 二、看板

**8. `JPivotTable` 的 `val` 不能是空数组。**
「清单式」透视（只列字段、没有度量）写 `val=[]` 会让 `add-charts` 直接失败。
给 `record_count`。**这是建盘最常见的单点失败，占掉半数以上的返工。**

**9. `add-filter` 的 `charts` 必须同一张表。**
跨表要**每表一次** `add-filter`，且**禁止**给它传 `--form-code`/`--form-name`（表单从 charts 推断）。

**10. `build_dashboards.py` 是非破坏的：已存在就跳过。**
所以**加图失败的盘，重跑会永远跳过、永远修不好**。
必须 `--recreate <盘名,盘名>` 先删后建。
失败明细在 `FAIL:<盘名>` 的**下一行缩进行**里，别只看 `OK:done 建 N / 失败 M` 的汇总。

**11. step 失败不要慌，先看这三样**：val 是否为空 / filter 是否跨表 / 字段中文名是否真实存在。

## 三、工作表与字段

**12. 公式 `$X$` 占位符必须在本表存在（含关联带出的字段）。**
写错只会在**真机补丁阶段**报「公式占位符对不上本表字段」，白等一轮。
→ 动笔时就用 `precheck.py` 静态查掉。

**13. `delete_widget` + `add_widget` 换控件类型会「换 model」。**
若该字段是**标题字段**，表单自己的 `titleField` 与**所有上游关联记录的
`options.titleField` / `showFields[]` 会全部悬空** —— 表现是列表里显示空白、下拉选不到，
**接口零报错**。
→ 换到标题字段时：要么改走 `update_widget` 原地改类型，要么用**原 key/model** 重新挂上去复原。

**13-b. 需求写「子表」时，`links` / `add_link_record.py` 都不产出子表 —— 必须建后单独转。**
产出的是普通 `link-record`：顶层无 `isSubTable`、`model` 是 `link_record_*`、`twoWayModel` 空。
**判据是需求原文有没有「子表」二字，不是控件长得像不像** —— `显示:"表格"` 落库是 `showType:"table"`，
明细区本身就是一张表格，**看着就是子表，设计器面板里仍叫「关联记录」**。
→ 4 步 + 自查见 `desform-link-record.md`「二-a」；全链路落点见 `fast-full-chain.md`「③-b」。
`save` / 回读 / `precheck` **全都不报**这一档（2026-09-20：16 表应用 53 个关联控件 `isSubTable` 0 个）。

**13-b-2. 转换时「整组套用 options」会误勾 `hiddenOnAdd`。**
转多个子表时把同一组 options 套给每个控件 → 需求没写「新增时隐藏」的子表也被勾上，
新增表单整块不渲染；而 `isSubTable`/`twoWayModel`/`showFields` 三项验收**全对**，
`save`/回读也全绿（2026-09-21 实测，用户报「XX 子表没有创建吗」）。
**「新增时隐藏」写在谁后面就归谁**：需求写「Tabs(新增时隐藏 …)」时归**页签容器**，
页签内的关联控件与 Tabs 之外的独立子表字段**都不带**。转换只动那四项，其余 options 保持原样。

**13-c. 子表转换会把 `model` 换名 —— 这是一次「引用面」级变更，静默面比 13-b 更宽。**
`link_record_*` → `sub_table_design_<key>` 之后，**凡存了旧 model 的地方全部悬空**：
他表 `showFields`/`filters.rules[].field`、`formula` 的 `$<model>$`、
**简流条件的 `field` 与 `data_update.updateFields[].field`**。
`save` / `precheck` / `check_node_contract` 全绿 —— 它们查结构，不解析引用。
两条硬约束：① 转换后拿旧 model 串 grep 全应用 design JSON + 全部 `processJson`，**0 命中才算转完**；
② **转换前抓的字段表快照（中文名→model）整份作废，建简流前必须重抓**
（复用旧快照 = 条件写到不存在的 model 上，不报错也不生效）。
简流条件里该字段的 `type` 仍是 `link-record`，**不是 `sub-table-design`**。详见 `fast-full-chain.md`「③-b」。

**14. `--rows` 默认 `0` = 不灌测试数据 → 灌数段应当整个跳过。**
**灌数是例外不是默认**：只有用户明确要求时才传 N；不传时跳过（否则它会

## 五、台账类回写（「按 X+Y 定位一行，没有就新建」）—— 2026-09-21 用户手工跑通后回抄

库存/余额/累计这类**派生台账**（本例的 `库存实时统计`）只有一种正确写法，
两条都不能省。**别用引擎的「没查到就自动建」**。

> ✅ **2026-09-21 源码定论（推翻同日早间的「无数据支不执行」）**：`data_branch` 能用，但网关名**必须是「数据分支」**
> （`BaseDataDelegate.noDataExecute()` 精确比较 `MiniDesConstant.DATA_BRANCH_NAME`，不匹配就终止实例并标已完成）。
> 技能已**四处**强制该名（`flow_dsl` / `miniflow_creator` / `build_flows` / `postbuild_flows.branch()`），
> 也提供 `upsert(表, cond, found=[…], missing=[…])` 把两支写在一处（默认展开成原生形态）。
> 同批按源码校正的几条：
> · 空值累加**静默不生效**（那一次累加被吞掉；源码里 `UpdateRecordDelegate:220 oldValue.toString()` 那条 NPE 路径
>   在 2026-09-22 进销存实测中并未抛出，表现就是不生效）→ 流程建的行由 `flow_rules` 规则 2 自动补 0，
>   **API/页面建的行要在 `DEFAULTS()` 里给初值 0**；
> · 「公式值累加把原值冲成 0」的真因是 **number/integer 目标走 `Integer.parseInt`**（`getUpdateValue`），带小数的值一律归 0 ——
>   构建器现在对 optType 增/减 + number/integer 目标写 `fieldType=money` 借 BigDecimal 路径，公式/运算结果都安全；
> · 比较符 le/lt/ge/gt 都是 `BigDecimal.compareTo`（`ConditionItemComparator:94-185`），「小于等于不命中」是判据读了输入行上的快照旧值；
> · 同表同事件多条流程**都会被触发**（信号名 `表码:流程表单id:事件` 每流程唯一，`BpmnCreator:366`；双流程对照实验确认）。
>   ⚠️ **但「都触发」不等于「都生效」**（2026-09-22 进销存 R5 实测，与早前「只跑一条」的观测在此和解）：
>   每条流程的 `cond` 是对**求值那一刻的当前行**判的，**不是触发时的快照**。所以 A 先跑并改了行上的字段后，
>   B 再判条件时读到的是**已被 A 改过**的值 —— 条件不再成立，B 就静默不执行，看起来像「只跑了一条」。
>   把两条改成链式（A 完成后由 A 去驱动 B 的触发字段）后，实测两条都执行。
>   **结论**：同表同事件的多条流程，只要它们的 `cond` 依赖同一批会被彼此改写的字段，就必须合并成一条多分支流程，
>   或改成显式链式；靠「它们都会触发」来保证都执行是不可靠的。
> 下面 ① 的分支语义不变。

**① `get_one(..., empty="分支")` + `data_branch()`，显式分支。**

```
get_one("库存实时统计", cond=[仓库编码, 产品编码], empty="分支")
data_branch(found=[update(..., {计数: inc/dec(...)})],      # 查到 → 只动计数
            missing=[add(..., {关联记录…, 计数: ref(...)})]) # 没查到 → 一次建对
```

`empty="新增"`（引擎自动建行）再 update 时，**建出来的行只有 update 节点里那几个字段**。
而 update 恰恰写不了「关联记录」这类字段（它有 `sourceCode/titleField/twoWayModel`
一整套关系，不是「一个值」），于是自动建出来的行**永远是残的**，且 save/deploy/回读全绿。

**查到那条支路只写计数**：`仓库编码/仓库名称/产品编码/产品名称` 都是 **link-field**，
link-record 一落就自动带出；重复写反而把已有值覆盖成空。

**② 要写的「关联记录」字段，得靠明细表上的隐藏中转字段带过来。**

明细行上原本只有「XX编码 / XX名称」这类 **link-field** —— 那是**纯文本**，
只有一个值、**不带指回记录的指针**，拿它写不进 link-record 字段（写进去页面上是空的）。

解法：明细表挂一个隐藏字段（规格
`"中转字段": {"<字段名>": ("<父表名>", "<父表字段名>")}`），默认值走设计器的
「其他工作表」取值 —— 落库是

```
advancedSetting.defaultValue = {type:"compose",
    value:"$<父关联控件的 key>.<父表字段的 model>$", format:"string",
    allowFunc:true, valueSplit:"", customConfig:false}
```

于是**每一行明细都物理带着**那个记录，流程 `ref()` 就能取到。

- 控件类型是 **`input`**（不是 link-record）：它只是个**搬运值的信封**，存的是记录 id；
  能写进 link-record 目标列，是因为**目标列**是 link-record，两边存的都是记录 id。
- ⚠️ `$key.model$` 前半是**本表那条关联控件的 key（不是 model）**，别写串。
- ⚠️ 默认值**只在新增那一刻算**。父单据的对应字段为空 → 这行明细的中转字段就是空的 →
  下游建出来的行仍然没有记录。**父单据必须先把那个字段写上。**
- 必须 `hidden=True`：机制字段，不该出现在表单上让人填。

**③ 各表的关联控件名不一样，别想当然。** 同样是「产品」，明细表里可能叫 `产品信息`、
`销售产品明细`、`采购订单产品明细`，而且**指向的表也未必是同一张**
（`销售产品明细` 指向的是**价格表**，不是产品表）。要写哪个字段、有没有这个字段，
**回读设计确认**；没有就退而写那两个文本 link-field（`saveType=save` 时写得进）。

**交付闸门**：`app_audit.py` 的 `[中转字段]` 段（存在 / 隐藏 / 默认值指向对的控件），
外加下一节那条「流程要用到的键」—— 中转字段被流程 `ref()`，不在明细行上就会直接报出来。

## 六、明细表要带哪些键：从流程推导，别照抄任何既有表

**任何被流程逐行处理的明细表**，`字段` 里必须带齐它那条流程**真正要读**的键。
清单是推出来的，不是抄来的：

1. 列出每条「主表触发 → 取多条明细 → 逐行调子流程」的流程；
2. 把子流程节点里 **`ref()` / `cond` 用到的每个字段**抄下来；
3. 核对该明细表的 `字段`——缺哪个补哪个。补法只有一种：
   **再建一条指向来源表的关联记录并 `带出`**（要拿关联记录本身，就把关联字段名写进 `带出`）。

按用途分，这些键通常是这四类（**字段名以你的表为准，下表只说明它从哪来**）：

| 用途 | 典型字段 | 从哪来 |
|---|---|---|
| 复制上游关联 | 上游实体（关联记录本身） | 关联该实体时带出 |
| 上游冗余 | 上游实体的名称 / 编码等 | 同上 |
| 归属 | **父单据号** | 再建一条关联指回父单据，带出 |
| 定位 | **`cond` 里用来定位本行的字段** | 同上 |

理由：约束 1（子流程只读本行）+ 约束 4（定位键要一起回写）+ 约束 5（回写靠同名桥）。
**不给这些键，流程建出来能发布、能跑，但一行都不写。**

## 七、API 造数与运行环境的几条事实（2026-09-22 四应用并行实测，冒烟/造数前先看）

**17. `add_data` 传了带「取关联字段」高级默认值的字段，服务端会用默认值覆盖你传的值**（开票金额←合同.待开票 这类）；不传则为空。
造数脚本对这类字段：新增后回读，不符就 `edit_data` 改回；冒烟断言按覆盖后口径写。前端「默认值=当前用户/部门/公式」在 API 写入时**不触发**，要自己填。

**18. 延时（`delay`）/ 定时 / 按日期触发节点靠后端异步执行器**；本机没起执行器时实例永远停在该节点（bpm 状态 2、无 endTime），
且 save/deploy/契约全绿。`data_add` 逐条新增是同步写库，不需要「等一等」。冒烟要核对实例 endTime。

**19. 汇总控件只在子记录**新增**时重算**，`edit_data` 改子记录不重算；`inner-record-count`（记录数量）与内嵌设计子表的汇总在 API 写入下可能为空。
大写金额（capital-money）是前端渲染时算的，API 写入不落库。这些字段的验收看页面，不看 API 回读。

**20. 子流程二次保存必须保住 `customProcessId`（= 自身 DB id）**：拿 `query_flow` 记录当 config 再 save 时该键可能为 None，
BPMN 退回 `<process id="process">`、主流程 callActivity 找不到定义、实例卡死。`save_flow` 现在对 subEvent 自动用 flow_id 顶上。

**21. 子流程内的排他网关实测恒走默认支。** 2026-09-22 进销存两例（`盘亏数量>0`、`result()>=0`）都没进条件支，
链路静默不记账、闸门全绿。判断写在子流程里时一律改用引擎原生的
`get_one(目标表, cond=[(字段, 规则, 值)], empty="分支") + data_branch(found=…, missing=…)`，或把判断挪回父流程。
`flow_rules` 规则 7 会告警。

**22. 排他网关的分支条件只支持「字段 vs 字面量」。** 值写 `ref()`/`var()` 时引擎仍按字面量比，条件恒假，
且实测**父流程卡在 bpm=2 不结束**（进销存「收款单-核销」）。要「字段对字段」就 `compute()` 算差额再判 `result()`，
或用上一条的 `get_one + data_branch`。`build_flows` 现在直接报错拦下。

**23. 公式里比较字典/选项值要用数值比较。** 字典落库是序号串（`"0"`/`"1"`），但 `IF($账向$=='0', …)` 这种
**字符串比较恒假**，`IF($账向$==0, …)` 才成立（2026-09-22 真机 A/B 实测）。

**24. 嵌套公式（公式引用同表公式）在 API/流程建的行上一律得 0。** 不限于「被流程更新的表」——
盘点明细、入库明细、价格表都中招，外层落 0 会让下游 `>0` 条件恒不成立。规格里把它展开成只引用基础字段的单层公式；
`precheck` 现在对**所有**嵌套公式提示。

**25. 公式控件在 API 写入的行上根本不计算，值是 `null`（不是 0）。** 比 #24 的范围更大——**单层**公式也一样
（2026-09-22 项目管理 R3：`工时成本小计 = 工时 × 单位工时成本`，两个源都非空，结果仍是 null），
其上游汇总跟着为空。**造数脚本对「被汇总引用的公式列」必须显式写值**；验收这类字段看页面，不看 API 回读。

**26. 汇总只在子记录**新增**时重算；`edit_data` 补完子行的值之后父表汇总不会再刷新，重存父记录也没用——
只能把子行删掉重建**（2026-09-22 项目管理 R3 为此多跑两轮修正）。

**27. 他表字段（`saveType=save` 快照）用 `edit_data` 整单回写会把旧快照原样写回。**
`edit_data` 是全量覆盖，「父记录重存一次就会刷新」在 API 路径上不成立。要让它按当前关联记录重取值，
必须**从 payload 里删掉该键**再存（项目管理 R3：`项目.总预算` 卡在 65000，删键重存后才变 161000）。

**28. 父子明细对只要子表也声明了指回父表的关联，就必须写「双向」。** 否则从子表侧建的行只填了子表那一侧，
父表的关联控件恒空 → **父表汇总恒为空**，而四道检查全绿、只有冒烟抓得到（项目管理 R3：17 对全中）。
`precheck.py` 现在对「被 summaries 引用、且对侧有回指关联」的 link 强制要求 `双向`。

**29. 带条件的汇总（`summary.options.filter`）在服务端重算时条件被忽略。** 形状写对、面板正常、六道闸门全绿，
但新增子记录触发重算后按**全部行**汇总（2026-09-22 项目管理 R4：加一条「待确认 600000」，「已确认收款」360000 → 960000），
并连累下游引用它的公式。**替代写法**：子表里加一个「计入合计」的公式列（满足条件取值、否则 0），对它做无条件求和；
或按状态拆成各自的关联/子表分别汇总。细节见 `desform-widget-options.md` 汇总节的红框。

**30. `capital-money`（金额大写）的 `moneyWidgetKey` 必须是**源金额控件的 `key`**，传中文名无效 ——
而它空了表单上只会显示一句红字。**
`CAPITAL_MONEY(name, money_field="<中文名>")` 里的中文名，靠**规格管道内的
`_post_process_widgets`** 解析成 key；**建后补丁脚本直接调用它时那一步不会跑**，
`moneyWidgetKey` 落成空串，表单显示「**关联的金额组件已失效**」，
而 `precheck` / `app_audit` / 契约检查 **全绿**（2026-09-22 实测：
建后把某字段从「金额」改成 `capital-money` 时踩到）。
补丁脚本一律传 `money_widget_key=<源控件 key>`，并顺手清掉继承来的金额 `placeholder`。

**31. 一切「控件引用控件」的字段都是悬空引用的高发区，而四道闸门都看不见。**
`linkRecordKey` / `showField` / `twoWayModel` / `moneyWidgetKey` / 汇总的来源控件 ——
只要补丁脚本**替换或新建**过控件，引用就可能落空，症状全是**运行态**的
（表单红字、下拉空白、汇总恒空），静态检查一律通过。#30 就是这么漏出去的。
**收尾扫一遍**：按名字收集全应用 `key` / `model` 池，把每个控件里的引用逐个比对
（`twoWayModel` 指的是**回指控件所在的另一张表**的 model，拿本表池去比会全是假阳性）。

**32. 一条记录的 link-record 值存成「对象」而不是数组时，`/desform/data/list` **整表 500**，
而 `list_data` 遇失败静默返回 0 条 → 界面看着像「这个表的数据丢了」。**
`queryLinkFieldData` 对字段值做 `JSON.parseArray`，日志里先有一条
`无法识别的关联记录值类型（{...}）` 的 WARN（**不带 dataId**，别指望从日志定位行）。

捞 id 只有一条路：**`/desform/data/calendarList` 不做 decoration**，一次返回全部记录；
`cardList`/`ganttList`/`statisticalValue`/`exportXls` 全都跟着 500
（`exportXls` 更彻底——**接口本身就是坏的**，干净表上也 500，与数据无关）。
拿到 id 后 `get_data` 读全量 → 改掉坏键 → `edit_data` 写回。
⚠️ **别指望 `superQuery` 兜底**：它不过滤（永不匹配的条件照样 500），拿去配
`batchUpdate` 会连着好行一起改。

**33. 树形表的 `__HAS_CHILD` 是**父节点**标记，只在**新增**子记录时由平台维护。**
用 `edit_data` 给**已存在**的记录补父级**不会触发**它，树形列表里父节点可能就不显示展开箭头，
而静态闸门全绿。手动补：`edit_data` 全量覆盖能写进去，取值**照抄同一张表里已有的写法**
（平台自建的是布尔 `true`，流程写的是字符串 `"true"`，**跟随同表既有值**，别自作主张统一）。
