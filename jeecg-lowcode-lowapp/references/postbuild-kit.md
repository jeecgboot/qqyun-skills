# 建后套件（postbuild_*）：规格语言写不下的东西，用声明式配置一次补齐

> **定位：提速，不改路线。** `build_app.py` + `app_spec.json` 照旧负责建壳；本套件只接管
> **建壳之后**那一段——以前这段靠现场手写 8~10 个补丁脚本（2026-09-21 CRM 24 表应用实测：
> 整轮 39.9 分钟里 **13.4 分钟在写脚本、12.9 分钟在想怎么写**，工具真正执行只有 4.1 分钟）。
> 现在改成：**写 4 份配置（只有中文名）→ 跑 6 条命令**。
>
> **不改任何现有脚本**，全部是新增文件；**覆盖不到的档位照旧回落手写**（见文末「回落」）。
> 每个脚本都支持 `--dry-run`（只报告不保存）且**幂等**，失败了改配置重跑即可。

## 一、建应用决策速查（先对着这张表分拣需求，再动手）

> ⛔ **下表是「查表」，不是动作 —— 真正的产物是 §1.1 的 `gap_list.md`。**
> 它回答「这条需求**落了没有**」；本节只回答「**落到哪**」。**只查表、不落清单 = 缺口静默**：
> 所有闸门都拿**规格**当真机基准比，**规格里本来就缺的那一项，它们一条都不报**
> （2026-09-28 进销存 47 表：`app_audit` 已经报「违例 0」，事后才发现编号规则 + 大半默认值整段没落，
> 白烧一整轮闸门 ≈5 分钟）。**写 `app_spec.json` 的同一轮就抄，别等 build 完再回头找。**

### 1.1 `gap_list.md` —— 分拣要在**写规格的同一轮**做完，不是 build 之后回头找

> ⛔ **上面那张表是「查表」，不是一个可执行的动作。** 真实事故（2026-09-28 进销存 47 表）：
> 表就在这一页、也读了，但清单是 **build 完之后边翻文档边凑**的 —— 于是漏掉「字典字段的默认值
> 必须写落库值」这一条，直到 `defaults` 跑完回读才暴露，白搭一轮补丁+回读。
>
> **做法**：写 `app_spec.json` 的**同一轮**里，把需求原文**逐条抄**成一张 `gap_list.md`，
> 每条给出落点。build 之后只做「执行 → 打勾」，**不做事后发现**。

骨架（放在工作目录，与 `app_spec.json` 同级）：

```markdown
# gap_list —— 需求条目 → 落点
# 规则：需求原文逐条抄，一条不漏；落点只能是 spec / struct_cfg / pb_flows / appconfig / 看板
| # | 需求原文（逐字抄） | 落点 | 状态 |
|---|---|---|---|
| 1 | 仓库状态（字典 仓库状态，**使用单选框**） | struct_cfg（改控件档位） | ☐ |
| 2 | 供应商价格表 产品信息（关联 产品信息 · 单条 · **必填**） | spec 的 `必填` | ☐ |
| 3 | 审批类字段一律**默认隐藏** | struct_cfg `OPT_FLAGS` | ☐ |
| 4 | 明细行的**校验 / 库存类只读字段**一律默认隐藏 | struct_cfg `OPT_FLAGS` | ☐ |
| 5 | 主数据表上的「下游单据列表」**新增时隐藏** | struct_cfg `OPT_FLAGS` | ☐ |
| 6 | 默认值：取关联记录「X」的「Y」 / 默认当前用户 / 默认当天 | struct_cfg `DEFAULTS()` | ☐ |
| 7 | **字典字段**的默认值 / 条件值 / 传参 / 筛选值 | ← 一律写 `itemValue`，**不是**文案 | ☐ |
| 8 | 看板单图筛选（「这张卡只统计 X=Y」） | 看板建后 `set-chart-filter` | ☐ |
| 9 | 编号规则（前缀 / 位数 / 含日序） | spec 的 `编号` | ☐ |
| 10 | … | … | ☐ |
```

- **「成组出现」的条目要逐条点名**（第 3~6 行最典型）：需求里「默认当前用户」这类句子
  会换个字段名重复出现几十次，漏配的在界面上**完全看不出来**（压根没有那行配置可查），
  `precheck` / `app_audit` / `postbuild_verify` **全绿**。数个数：需求声明 N 条 vs 清单 N 条。
- 第 7 行是**跨 skill 通用条**（lowapp 按钮条件 / miniflow `cond`·`updateFields`·`pass_` /
  看板 `conditionFields`），三处都是**静默失效**且结构闸门一条都拦不住 —— 见 `engine-contract.md` 5-b。
- **跑闸门之前对着这张表逐条打勾**；有 ☐ 就别跑（这就是下面第 ⑦⑧ 段那句「自问」的可执行形式）。

## 二、运行顺序（6 条命令）

> ⚠️ 结构配置文件叫 **`struct_cfg.py`**，不要叫 `struct.py`：与标准库 `struct` 同名，配置目录里任何
> `import requests` 的脚本都会崩在 `zipfile → struct.calcsize`（2026-09-22 四个应用里三个撞到）。
> `postbuild_run.py` 两个名字都认，优先新名。

公共参数：`--api-base URL --token T --tenant-id N --app-id A`（下文记作 `$C`）。
工作目录默认是该应用的工作目录 `{系统临时目录}/jeecg-lowcode/<英文简称>_<时间戳>/`（按 app_id 从 `app.json` 反查；没开过 `--new` 时是 `jeecg-lowcode/<app-id>/`），快照 probe/dicts 与配置文件都在这里。

```bash
python scripts/postbuild_probe.py     $C                                  # ① 快照：probe.json + dicts.json（只读）
python scripts/postbuild_struct.py    $C --config struct_cfg.py   --dry-run   # ② 先看计划，MISS=0 再去掉 --dry-run
python scripts/postbuild_probe.py     $C                                  # ③ 转过子表/改过名 → 必须重拍快照
python scripts/postbuild_defaults.py  $C --config struct_cfg.py               # ④ 默认值（可与 ② 同一个配置文件）
python scripts/postbuild_flows.py     $C --config pb_flows.py             # ⑤ 简流（别叫 flows.py：与 flow_dsl 的 flows.py 撞名）
python scripts/postbuild_subpub.py    $C                                  # ⑤.5 ★ subEvent 子流程补发定义 key（见下）
python scripts/postbuild_subfix.py    $C --expect 25                      # ⑤.6 ★ 子流程收尾（建完父流程后必跑，见下）
python scripts/postbuild_appconfig.py $C --config appconfig.py            # ⑥ 按钮/视图/导航/开关
python scripts/postbuild_verify.py    $C                                  # ⑦ 只读验收（引用完整性+子表不变量+流程启用+按钮绑定）
python ../jeecg-lowcode-miniflow/scripts/check_node_contract.py ...       # ⑧ 简流契约闸门（照旧必跑）
```

> **⑤.5 `postbuild_subpub.py` —— 建过 subEvent 子流程就必须跑这一条**（2026-09-22 进销存 47 表实测）：
> 批量建出的子流程记录里 `customProcessId` 是空的 → 引擎把 BPMN 定义 key 拼成坏 key `process` →
> 父流程 `callActivity` 永远找不到定义。**症状是静默的**：save/deploy 全绿、条数对得上、
> `processStatus=1`，只有简流契约闸门（⑧）和 `build_flows` 的 barrier 报「N/N 条子流程未注册」，
> 主流程一条都不建 —— 白掉一整轮。脚本幂等，25 条约 42 秒；
> `--dry-run` 只看计划、`--check-only` 只核验、退出码 2 = 有失败项。
> ⚠️ **`postbuild_run.py` 里没有这一段**，必须单独插在「建子流程之后、建父流程之前」。
> 判据用 `queryById.processXml`（base64 解码后 `<process id="process<DBid>">`）；
> ⛔ 别用 `/act/process/list` 核验（实测 read timeout），也别拿记录里的 `customProcessId` 当判据
> （`saveFlow` 不回写该列，回读恒为 `None`）。详见 `fast-full-chain.md` ④。
>
> ✅ **2026-09-28：`build_flows` 的 ①.5 屏障也改用同一条权威判据了 —— 补发后直接原命令重跑即可。**
> 以前屏障判 `/act/process/list`，于是本脚本报「30/30 已就绪」、屏障同时报「30/30 未注册」，
> 补发后重跑**仍然全红**（进销存 47 表实测，白烧一轮）。现在屏障是
> 「`queryById` 权威判 + `/act/process/list` 只作并集兜底（只救误报、不一票否决）」。
> **标准节奏**：`build_flows`（建子流程，被屏障拦下 = 预期）→ ⑤.5 本脚本
> → **`--check-only` 确认 `异常 0`** → **原命令重跑 `build_flows`**（屏障自动放行）。
> ⛔ `--force` 只在 `--check-only` **真报缺口**且你决定带病继续时才用 ——
> 它会把「没注册」和「判据读不到」一起放行，两者运行期都是 `FlowableObjectNotFoundException`。

> ⚠️ **⑤.6 `postbuild_subfix.py` —— 建过子流程就必须跑这一条**（2026-09-23 进销存 47 表实测）：
> `build_flows` 的「父流程回填趟」在父流程建完之后**又重存了一遍子流程**，
> 把其中一部分的 `startType` 从 `subEvent` 打回 **`tableEvent`**（它们会变成普通表事件流程、
> 在上下文表被写时**误触发**），同时清空 `subFlowSourceInfo`（「被以下工作流触发」）。
> ⑤.5 的 `postbuild_subpub.py` **只认已经是 `subEvent` 的**，修不了这一档。
> 症状全静默：`save`/`deploy`/条数/`app_audit` 全绿，只有 `check_node_contract`
> 的「其中子流程 N 条」会少（实测 19 而不是 25）。脚本幂等，从各父流程 `subFlowList` 反推要修谁；
> `--check-only` / `--dry-run` / 退出码 2 = 有失败项。**排位：建完父流程之后、⑧ 契约闸门之前。**
> 详见 `engine-contract.md` #7-d。
>
> ⚠️ **⑥ 的 `--only views` 在本后端 ≈ 50 秒/表**（2026-09-23 实测单次 `config_table` = 53s；
> 47 张表 ≈ **40 分钟**），而且**全程零输出**——看起来像卡死，其实在跑。
> **不要盲等**：先用一次单表调用测速，再决定「等 / 后台跑 / 跳过」。
> 「列表视图开数据统计」不是需求项，跳过的代价只是列表底部没有合计行。

**一条命令版（推荐）**：把 `struct_cfg.py` / `pb_flows.py` / `appconfig.py` 放进同一个目录（缺哪个跳过哪段；`--work DIR` 可把 probe/dicts 也放进自定义目录），

```bash
python scripts/postbuild_run.py $C --dir <配置目录> [--dry-run] [--from struct|defaults|flows|appconfig|verify]
```

它就是按上面 ①~⑧ 的顺序逐个起子进程，任一段非 0 立刻停并提示 `--from` 续跑点。
⚠️ **它不含 ⑤.5（`postbuild_subpub.py`）** —— 建过 subEvent 子流程的应用，要在 flows 段之后单独补跑那一条。
⚠️ 全新应用上 `--dry-run` 只对 `struct` 段有意义：没真保存，改名/转子表没发生，后面几段会按旧名字报 `MISS`。
正常做法：`struct` 单独 dry-run 看一眼计划 → 去掉 `--dry-run` 整条跑。

- **退出码 2 = 有未解析的名字 / 失败项**，看 `MISS:` / `FAIL:` 行改配置重跑；**0 才往下走**。
- 顺序不能换：②改名/转子表 → ③重拍 → ④⑤⑥ 都按**改名后**的名字解析；⑤ 在 ⑥ 之前（按钮按流程名绑定）。
- ⑦ 自带 `--self-test`（往内存副本里注入 6 类坏引用，确认检查器本身没瞎）。

> ⛔ **②~⑥ 是一组「一次列全、一次跑完」的补丁；⑦⑧ 是只读闸门，跑完闸门就别再补丁（2026-09-28 进销存 47 表实测）。**
> ⑦⑧（以及 `fast-full-chain.md` 的 `app_audit`）查的都是**真机现状**，而 `app_audit` 实测 ≈4.6 分钟/遍。
> 只要在闸门**通过之后**再补任何一处控件级改动，就得整轮重跑 —— 而重跑的结论和重跑前是同一句话。
> 2026-09-28 实测：`app_audit` 第一遍已「违例 0 / 提示 0」，之后才去补「仓库状态改成单选框」这条需求细节，
> **白烧一整遍（≈5 分钟）**。
> **做法**：把需求里所有「规格语言表达不了」的项先拉成一张清单 —— `RENAME` / `DEFAULTS()` / `OPT_FLAGS` /
> `WIDTH` / `SUBTABLES` / `NUMBER_RULES` / `LINK_RECORD` / 看板单图的 `config.filter` / 按钮 ——
> 全部写进 `struct_cfg.py` + `appconfig.py` 并回读确认，**再**跑 ⑦⑧。
> **判据：跑闸门之前对着 §1.1 的 `gap_list.md` 逐条打勾，有 ☐ 就不许跑。**
> ⛔ 原文写的是「自问一句『还有没有没落的需求项？』」—— **那是不可执行的**（人对这个问句
> 永远答「应该没有了」，而清单本来就是因为答不出才存在的）。**问句已经升级成清单**：清单是
> 需求原文逐条抄出来的，**答不出来的地方一眼就能看见**（就是那些没被抄进去的行）。
> 闸门报出的违例当然要改，但改完算「同一批补丁的续做」；若违例逼出了**新的补丁清单**，
> 就一次性做完再跑下一趟，别一条一条往返。

## 三、配置写法（全部写中文名；同名时默认取非分隔符控件，点名分隔符写 `'名称#divider'`）

> 下面的片段够写大多数应用。**完整样例**（24 表 CRM：7 个子表、132 个默认值、22 条简流、18 个按钮）在
> `references/postbuild-examples/crm/{struct,flows,appconfig}.py`——写法拿不准时按关键字 grep 它，**别通读**。
> 它同时是套件的回归基线：改了 `postbuild_*.py` 之后，对那套 CRM 应用跑
> `postbuild_run.py --dir references/postbuild-examples/crm --dry-run`，struct/defaults/flows/appconfig 四段都应是 0 差异。

### 3.1 `struct_cfg.py` —— 结构补丁（每个变量都可省略；`RENAME` 最后执行，其余项用**改名前**的名字）

#### 存量应用怎么摘掉 `RENAME`（2026-09-24 进销存 47 表实测走完一遍）

`RENAME` 的**代价是可测的**：它会把这个补丁趟的名册撑大。
进销存实测 —— `RENAME` 233 条牵动 **47 张表**，而其余项
（`TO_LINKFIELD` 3 表 + `OPT_FLAGS` 7 表 + `NUMBER_RULES` 1 表 + `SUBTABLES` 4 表）并集只有 **12 张**。
**清掉 `RENAME` 后该趟从 47 张表降到 12 张**（`SAVE` 行数直接可数）。

摘除配方（三步，第 ② 步是唯一容易错的地方）：

1. **把规格改成最终名** —— 别手写，复用 `app_audit.apply_rename(spec, struct, carry_namespace='local')`，
   它已覆盖全部命名空间（字段/必填/字典/编号/公式**含 `$占位符$`**/类型/选项/静态三兄弟/
   日期粒度/中转字段/标题/`links.字段`/`带出`/`带出映射`/`summaries` 三字段/`layouts`）。
2. ⚠️ **先把 `links[].带出` 拆一遍**，再调 `apply_rename` —— 顺序不能反。
   在**旧命名空间**里，同一个名字才能同时查本表与目标表两张改名表：
   ```python
   lf = REN.get(本表, {}).get(x, x)      # 本表最终名
   tf = REN.get(目标, {}).get(x, x)      # 源表最终名
   if lf == tf: 留在 带出
   else:        挪进 带出映射 {lf: tf}    # 带出只能同名，名字分家了就必须走映射
   ```
   进销存 47 表实测：403 项带出里 **17 项**要走映射 —— 除了 `联系人名称`/`采购订单编号` 这两组，
   还捞出 **9 处「半边改名」**（`收款计划.销售订单金额(含税)` 本表没改、源表改成了 `…/元`，
   此类必报「带出找不到字段」）。
3. **自检要按表作用域**，不能用全局旧名集：`联系人名称` 在报价单是要改的旧名，
   在**客户本表**却是最终名；`采购订单编号` 在采购入库要改、在采购订单自己不改。
   全局比对会把这一档全判成残留。进销存 47 表实测核 3405 个名字、残留 0 才放行。

> ✅ **验收方式（别只看闸门）**：用新规格**另建一个应用**（配 `RENAME={}` 的 struct），
> 与旧应用的真机设计**逐表逐字段对比**。比的时候 ⚠️ **model 字面量每次建表都重生成，
> 必须先反查成「表名.字段名」再比** —— 不反查的话每个公式、每个他表字段都会假报差异
> （`$money_1790231813550_461993$` 这类）。进销存实测：47 张表的字段名集合、控件类型、
> 关联目标表、他表字段源绑定、公式表达式**全部一致**，且 `precheck` 提示数 33→33、流程违例 0。

### 3.2 `DEFAULTS()` —— 默认值（写在同一个 `struct_cfg.py` 里即可；用**改名后**的名字）

> ⛔ **默认值必须拿需求原文「逐条点名核对」，禁止照印象铺。**（2026-09-24 生产管理 53 表实测）
> 需求里「默认值：取关联记录「X」的「Y」」「默认当前用户」「默认值函数计算：A−B」这类句子
> **换个字段名重复出现几十次**，而漏配的那几条**在界面上完全看不出来** ——
> 因为压根没有那行配置可查，`precheck` / `app_audit` / `postbuild_verify` 全绿。
> 本轮：用户点到 `原材料入库.入库单据名称` 一处，顺着对原文又查出 **3 处**
> （`原材料质检记录.不合格数量`、`产成品入库明细`… 的函数默认值等）。
> **核对口径**：从需求原文抽出所有「默认…」条目 → 逐条到真机 design 上验
> `advancedSetting.defaultValue.value` 非空（空 compose 壳 `{type:'compose',value:''}`
> **会覆盖** `options.defaultValue`，看着像配了其实没有）。
> 清单与做法见 `app-prompt-skeleton.md` **第五节「成组出现的需求要按原文逐条点名核对」**。
> ⚠️ 默认值**在 API 写入时不触发**，验完要让用户**在界面新增一条**看带不带得出来。

> ⚠️ **凡是会被流程 `inc`/`dec` 累加的数值列，都要有初值 0。**
> 空值上做「增加/减少」是**静默不生效**（那一次累加被吞掉，不是报错也不是 NPE），
> 而且 2026-09-22 进销存实测：`inc` 撞 null 还会连累**同一节点里其余字段一起不写**。
>
> 三条路径要分清（2026-09-22 进销存 R4/R5 两次实测更正）：
> · **流程 `add()` 建的行** → `flow_rules` 规则 2 自动补 0，不用管；
> · **页面新增的行** → 这里的 `static(表, 列, 0)` 生效；
> · **接口（`add_data`）建的行 → `static()` 不落**，默认值整套（`static` / `func` / 取关联字段）在 API 写入时都不触发。
>   所以**造数脚本必须自己把这些列显式写 0**，别指望 `DEFAULTS()` 兜住。
>
> `precheck.py` 会逐表提示缺初值的累加列。

> ⚠️ **默认值没有任何闸门对照需求核验 —— 清单是手抄的，漏了静默。**
> `precheck` / `postbuild_verify` / `app_audit` 都不看 `DEFAULTS()`（`app_audit` 只比 `app_spec`，
> 而默认值不在 spec 里），没列到的字段就是没默认值，全绿放行。
> 2026-09-28 实测：需求声明「默认当前用户」16 条只写了 15、「默认当前部门」14 条只写了 12，
> 另有 `static` / `lookup` / `take` 各整行漏写一条，四道闸门全是 0。
> 漏的位置有规律——**跳到下一张表时漏掉中间那张**。
> **交付前逐类数个数**（需求声明 N 条 vs 清单 N 条），或解析需求的「默认」声明逐字段对照真机。

- **`msg(标题, 正文, ...)` 的第一个参数就是收件箱里的消息标题**：写具体的（「新任务通知」「Bug待验证」），别写「系统消息」——照抄出来收件箱全是一样的标题（2026-09-24 任务-一句话8）。
- **累加 / 扣减**：`upd('激活', 'Bug', [('状态', '激活'), ('激活次数', inc(1))])`，`dec(n)` 扣减——与 `flow_dsl.inc/dec` 同写法，落成 optType=2/3（逐字段，可与设值混写）。
- **审批人取表单里的选人字段**：`appr('需求评审', '需求', '评审人')`（第三个参数 = 本表选择用户字段名）。
- **写日期字段的「当前日期/时间」**用 `sysdate()`/`systime()` 照写即可，`miniflow_creator` 会对日期控件自动改成毫秒变量（引擎 nowDate 写的是字符串，见 miniflow gotchas「2026-09-24 补正」）。
- ⚠️ **`upd(..., src=<节点>)` 的来源类型要跟真实来源节点走，不能一律 `search`。**
  来源是 `get_one` 时 `search` 正确；来源是 **`get_more` 时引擎要的是 `getMore` + `formTableSourceGetDataType=1`**。
  类型不匹配的症状是**整批静默不写**（按钮点了、明细一行没变），而 save/deploy 全绿
  （2026-09-22 库存应用「确认入库」实测）。**建完回读 `attr.formTableSourceNodeType` 断言**（读 `attr.*`，不是节点顶层），
  判据 = `miniflow/node-contract.md` §8.4 那张类型表（`table`/`search`/`getMore`/`plus`/`function`）；
  权威页另有 `miniflow/miniflow-node-types.md` §三 3.1 与 §十三（get_more）。
- 办理人：`appr(name)` / `fill(name)` 默认=发起人；`fill('售后处理', '服务工单', '售后技术人员')` = 取表单成员字段；
  `appr(name, users=['admin'])` = 指定成员（**裸账号**，别带 `user.` 前缀）；
  `appr(name, roles=['部门经理'])` = 按角色（角色名或 roleCode，租户里没有会报错）——按钮流「重新提交」
  要和表事件审批用同一套角色时用它（`fill()` 同样支持 `users=` / `roles=`）。
- **节点字段权限 `perm()`**：重跑幂等（已有规则行按 id 更新）；同一流程有同名节点必须给 `nth=`，否则报错；
  **子表列不能单独给权限**，只能按整张子表写子表名（写列名会报错并提示子表名）。
- ⚠️ **配置文件里别用单字母全局变量名**（`T`、`C`、`M`、`w`…）：配置是 exec 进脚本全局执行的，
  同名会盖掉助手函数，报 `'str' object is not callable`（项目管理-速测17/18 两次）；同理 `__file__` 指向脚本本身，
  配置里读文件一律写**绝对路径**。
- 字典字段的固定值用 `dv('字典名','文案')`；静态字典（radio/select 手写选项）直接写文案。
- 已存在的同名流程**跳过**；要重建用 `--replace 流程名,流程名`（之后重跑 ⑥ 重绑按钮）。
- `--dry-run` 会把配置生成的结构与**现网已部署流程**逐条比对，输出 `SAME` / `DIFF` / `NEW`。
- ⚠️ **同一条子流程只能有一个调用方**（子流程里用了 `ref()` 取本行时）：回填把本行引用绑到调用方的取数节点，
  第二个调用方调用时取值全空。每个调用方各建一条子流程；precheck / build_flows 回填都会拦（进销存-速测18 S4）。
  **定时父流程**（gotchas #127 手拼）调子流程时，`postbuild_subfix.py` 会从父流程节点补齐子流程的
  `isSubStart` / `subFormTableObject` / 本行取值（以前只补 `subFlowSourceInfo`，契约闸门报违例）。
- **系统消息 `msg()`**：收件人/正文引用表单字段时，引擎要的是两种**不同**的落库形态（6 键 `var.` 条目 / 4 键 ref
  → md5 → base64 存 `jsonContext`），肉眼看不出来、save/deploy 全绿但消息发不出去 —— 一律用 `msg()` 生成，
  别手写。`to=` 传 `start(t,成员字段)` 或 `search(get_one节点, t, 成员字段)`，正文里用**字段中文名**写 `{…}`
  占位符（字段名写错会直接报错）。消息节点必须挂在被引用节点**之后**、且在同一条链上。
- **子流程两处别漏**（都是闸门只报提示、但真会不通的档）：
  ① 流程级 `pj['attr']['subFormTableObject']` 要与 `start` 节点那份、`formTableList[0]` **三处一致**
  （空壳时子流程内 `ref()` 全取空、分支永远走 missing）；
  ② `subFlowSourceInfo` 必须在**该子流程最后一次保存时**显式回填 `[{mainProcessId, mainProcessName, nodeName}]`
  —— 重存父流程**不会**补（gotchas ③ 已证伪旧提示语），且子流程之后再被存一次就又清空。

## 四、已经固化进脚本的坑（**不用再记、不用再试**）

| 坑 | 现象 | 脚本怎么处理 |
|---|---|---|
| 汇总 `linkTable` 存的是明细**控件 key** | 转子表时顺手改成 `sub_table_design_…` → 面板显示裸字符串、汇总失效 | `SUBTABLES` 只动 `isSubTable` / `model` / 两侧 `twoWayModel` |
| 字典选项落库值是序号串 | 条件/默认值写文案 → 永远不匹配 | `dv()` / `static(..., 字典名)` |
| 字典列表接口的键名是 `dictItemsList` | 取不到选项 | probe 已处理 |
| 整单保存时字典控件的 `remote` 要保持 `'dict'` | 回写设计时容易带丢 | 保存前统一复位 `remote='dict'` |
| 建按钮会**自动生成占位流程**并写进 `processId`（纯表单按钮也会） | 按钮点了跑空流程；应用里多出一堆孤儿流程 | 建完立刻换绑/清空 → 回读 → 删占位 |
| 按钮 CLI：`list` 返回 `result.buttons`；stdout/stderr 混排；`update` 的 `changes:{}` 写法以前静默无效 | JSON 解析失败；绑流程没绑上却回 success | 已封装；CLI 本身也已修（`changes:{}` 与顶层字段两种写法都生效，2026-09-21 真机回归） |
| 导航隐藏接口对任何输入都回「编辑成功」 | 以为隐藏了其实没有 | 回读 `hideFlag` 断言 |
| 并行建表的菜单 `orderNum` 错乱且重复；首个分组 `parentId` 是 NULL、其余是空串（后端 `ORDER BY parent_id, order_num`） | 分组/组内顺序全乱；NULL 的分组永远排最前，只改 `orderNum` 修不好 | `MENU_ORDER`：先把 NULL 归一成空串 → 分组与菜单各发一次 `changeOrder` → 按**接口返回顺序**回读；`postbuild_verify.py` 另查排序号重复与 parentId 混用 |
| 功能开关有父子联动（见 `desform-lowapp-utils.md`「父子联动规则」） | 只发一部分容易父子不一致 | 13 项一次全发，已全开的表跳过 |
| 「= 当前日期」插 `+0D` 运算节点 | 契约闸门判违例 | `sysdate()` / `systime()` 系统变量 |
| 节点 id 有前缀约定（审批/填写、网关、延时各不同） | 手写容易写错 | 自动取号 |
| 审批后接「意见分支」（suggest，手拼）保存报 mxGraph `getAbsolutePoints()` NPE（2026-09-21 本机三种 id 写法均失败） | 流程存不上 | **改用审批结果分支 `result_branch(ok=[…], reject=[…])`**（2026-09-24 实测保存/发布/通过支/否决支全通）；构建器自动给前置审批节点补 `hasResultBranch` / `addable=false`。冒烟验否决支在 approval 里写 `'reject': ['节点名']` |
| 按钮条件写「流程状态」原样落库 | 按钮永远不按条件显示；`postbuild_verify` 报「不是本表字段」 | `C('流程状态', 'ne', '处理中')` 自动落成 `bpm_status` + 编码（1 待提交 / 2 处理中 / 3 已完成 / 4 已作废）；创建人/创建时间等系统字段同理 |
| 数据过滤条件裸放根层 | 界面不显示、落库被吞 | 自动包进筛选组 |
| `build_flows` 父流程回填趟重存子流程 → `startType` 掉回 `tableEvent`、`subFlowSourceInfo` 清空 | 子流程变成普通表事件流程、**误触发**；`save`/`deploy`/条数/`app_audit` 全绿，只有 `check_node_contract` 的「其中子流程 N 条」偏少 | `postbuild_subfix.py`（⑤.6）：从各父流程 `subFlowList` 反推，重存 `startType=subEvent` + 回填 `subFlowSourceInfo` + deploy；幂等 |

## 五、回落（保证稳定的那条底线）

- 套件是**加速器，不是唯一入口**。某个档位配置里写不出来（或脚本报错一时修不了）→
