# 定时批量处理 + 逐行通知 子流程示例

> **结构说明：**
> - **适用场景**：定时触发扫描工作表 → 满足条件的多条记录批量改状态 → **逐条给记录上的用户（select-user 字段）发系统消息**（订单超时自动处理、到期提醒等）。
> - **为什么必须子流程（用户 2026-09-09 定论，gotchas #57）**：消息节点直连多记录 getMore 不逐行执行（主流程只处理单记录）。正确结构 = 主链 `function(-1D) → data_get_more(双条件) → data_update(getMore 批量) → callActivity(子流程 isMulti 逐行)`，子流程（subEvent 三层）内唯一节点 message_system，收件人=该行客户（var `nodeType='search'` 引用父 getMore 行）。
> - **2026-09-09 两版实证**（初版直连消息被用户驳回 → 子流程版双回读+引擎 key 核验通过）。本模板 = 修复版整链，**只改 ①–⑤ 常量即跑**。
> - 关联：create-flow.md **组合 H**（同款简版+理论）、gotchas **#57/#47/#41/#49**、主子流程配置示例.md（callActivity 生产形态附录）。
> - ⚡ **全新建一律先跑 `scripts/timer_job_runner.py`**（4 子命令 shell/announce/scan/check，3.4-4.5s 实测，2026-09-09；scan 子命令已含 data_update 批量改与逐行通知，check 子命令含 data_branch 分支）；本模板只留给改已有主流程等 runner 未覆盖场景。

## 关键注意点

1. **顺序不能反**：子流程先建先发布（callActivity 需要 sub_id / customProcessId），主流程后建后挂。发布走 gotchas #47（回查 updateCount → POST designer saveFlow 补 customProcessId → PUT deployProcess），漏一步引擎 key 会拼错（processnull）。
2. **改已有主流程**（不是新建）：只跑 B2–B5 段改造 + C/D——query_flow 拉最新 → 摘除旧 message_system 节点（若在）→ B4 挂 callActivity → save(update_count=rec.updateCount) + deploy；gm 的 formTableList 条目同样补 isSubStart。
3. **子流程消息收件人 var = `nodeType:'search'`**（子流程行上下文）；主流程直连的 `'getMore'` 形态运行不逐行（#57）。消息正文要引用字段 → 组合 G/gotchas #55（md5+base64 jsonContext），纯静态文案免。
4. **date 字段非 timestamp**：本表下单时间是 date（非 datetime），dateFunctionFormat argument/result='date'；datetime 字段才用 'datetime'。date 偏移单位：+24H/-1D 均可（引擎 ISO 周期语义，-1D=24 小时前，09:00 跑即取昨日 09:00 前的记录）。
5. 字段 model 一律 fetch_form_fields 现解析，禁止照抄旧值（表单重建后 model 会变）。
