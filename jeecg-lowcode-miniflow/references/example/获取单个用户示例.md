## 一、精简示例（AI 速读版）

获取单个系统人员/部门/角色（get_one_sysinfo，实际类型 data_get_udr_one）共 6 种取数方式：selectType 1-3 从工作表字段取，4-6 从组织架构查询。

### 1. 从工作表用户/部门/角色字段获取（selectType 1-3）

```python
# ① 用户字段：取工作表用户组件字段对应的用户
{
    "type": "get_one_sysinfo",                    # 实际生成 type=data_get_udr_one
    "name": "从用户字段获取",
    "getType": "user_field",                      # → selectType=1（查 sys_user）
    "sourceTaskId": "start",
    "fieldIds": ["create_by"],                    # 工作表中的用户组件字段 model
    "noDataType": 1,
},

# ② 部门字段：getType="dept_field"（selectType=2），fieldIds 填部门组件字段
{
    "type": "get_one_sysinfo",
    "name": "从部门字段获取",
    "getType": "dept_field",
    "sourceTaskId": "start",
    "fieldIds": ["select_depart_1776156404894_859529"],
    "noDataType": 1,
},

# ③ 角色字段：getType="role_field"（selectType=3），fieldIds 填角色组件字段
{
    "type": "get_one_sysinfo",
    "name": "从角色字段获取",
    "getType": "role_field",
    "sourceTaskId": "start",
    "fieldIds": ["org_role_1776156424044_622887"],
    "noDataType": 1,
},
```

### 2. 从组织架构查询（selectType 4-6）

```python
# ④ 组织人员：按姓名精确匹配
{
    "type": "get_one_sysinfo",
    "name": "从组织人员中获取",
    "getType": "org_user",                        # → selectType=4（查 sys_user）
    "conditions": [
        {"rule": "eq", "ruleName": "等于", "valueType": "1",
         "val": "张丽",
         "field": "realname",                     # 系统表字段：姓名
         "columnName": "姓名", "type": "text", "valType": "text",
         "dbType": "string"},                     # ⚠️ 系统表条件带 dbType
    ],
    "noDataType": 1,
},

# ⑤ 组织部门：按部门名称模糊查询
{
    "type": "get_one_sysinfo",
    "name": "从组织部门中获取",
    "getType": "org_dept",                        # → selectType=5（查 sys_depart）
    "conditions": [
        {"rule": "like", "ruleName": "全模糊", "valueType": "1",
         "val": "销售",
         "field": "departName",                   # 系统表字段：部门名称
         "columnName": "部门名称", "type": "text", "valType": "text",
         "dbType": "string"},
    ],
    "noDataType": 1,
},

# ⑥ 组织角色：按角色名称模糊查询
{
    "type": "get_one_sysinfo",
    "name": "从组织角色中获取",
    "getType": "org_role",                        # → selectType=6（查 sys_role）
    "conditions": [
        {"rule": "like", "ruleName": "全模糊", "valueType": "1",
         "val": "管理员",
         "field": "roleName",                     # 系统表字段：角色名称
         "columnName": "角色名称", "type": "text", "valType": "text",
         "dbType": "string"},
    ],
    "noDataType": 1,
},
```

### 3. getType 枚举速查

| getType | selectType | 数据来源 | 查询的系统表 |
|---|---|---|---|
| `user_field` | 1 | 工作表用户组件字段（fieldIds） | sys_user |
| `dept_field` | 2 | 工作表部门组件字段（fieldIds） | sys_depart |
| `role_field` | 3 | 工作表角色组件字段（fieldIds） | sys_role |
| `org_user` | 4 | 组织架构查询（conditions） | sys_user |
| `org_dept` | 5 | 组织架构查询（conditions） | sys_depart |
| `org_role` | 6 | 组织架构查询（conditions） | sys_role |

### 4. 生产数据提炼的关键知识点

1. **selectType≤3（取表单字段）时 formTableId 固定为 `form_start_<表单code>`**（不是节点 ID）；selectType≥4（组织架构）时为 `sys_user`/`sys_depart`/`sys_role`（脚本生成 `form_{节点ID}_sys_user` 格式，两者前端均兼容）。
2. **attr.tenantId 必须是当前登录租户**（字符串）。附录示例里的 "2" 只是生成环境的租户值，**禁止抄写**——写错租户时系统表查询按租户隔离会查不到、设计器值显示异常（2026-09-09 用户 UI 实测纠正）。
3. **系统表条件 field 用系统表列名**（realname/departName/roleName），不能用工作表字段 model；条件带 `dbType: "string"` 无害，UI 重存会丢弃它且不影响保存/显示（勿照附录强行补回）。
4. **delegate 固定为 `${getUserDeptRoleOneDelegate}`**；节点 type 为 data_get_udr_one，formTableList 条目 nodeType 为 getUserDeptRole（脚本自动生成，无需手写）。
5. **字段获取（1-3）不写 conditions**，用 fieldIds（即 userFormTableField/deptFormTableField/roleFormTableField）；组织架构查询（4-6）才写 conditions。
6. **noDataType 生产数据统一为 1**（查不到继续执行）。⚠️ 旧结论「节点 content 为 getType 码、仅展示用途」已推翻（2026-09-09 用户 UI 实测），详见下方「5. 落库修正」。

### 5. ⚠️ content / tenantId 落库修正（2026-09-09 用户 UI 实测纠正，必读）

设计器画布上节点卡片底部那一行"来源"，就是节点**顶层 `content` 键**，UI 原生保存必写 `工作表 "<attr.formTableName>"`：

- selectType 1-3（从工作表字段取）→ `工作表 "来源工作表名"`
- selectType 4-6（从组织架构查）→ `工作表 "用户表"` / `工作表 "部门表"` / `工作表 "角色表"`

**三个常见落库错（builder 产物）与后果：**

1. `content` 被写成 getType 码（`user_field`/`org_user`…）→ 画布卡片显示英文取数方式码；
2. `content` 缺失 → 画布卡片显示占位「设置此节点」；
3. `attr.tenantId` 落到其他环境租户值 → 系统表查询租户隔离失效、设计器值异常。

save 前对每个 data_get_udr_one 节点自愈：

```python
# ⚠️ builder（经 build_process_json 生成单数 udr 节点、config 未给 formTableName 时）
# 可能连 attr.formTableName 都不落——有 formTableCode 却无名，必须同批补，
# 否则上方 content 公式得到 `工作表 ""`（画布空来源行）。2026-09-09 实证。
node['attr']['formTableName'] = <来源工作表中文名>
ftn = node['attr'].get('formTableName') or ''
node['content'] = f'工作表 "{ftn}"'         # 与 attr.formTableName 同源
node['attr']['tenantId'] = <当前登录租户>     # 禁止抄示例/其他环境租户值
```

改已有流程时同样检查既有 udr 节点的这三个键（content/formTableName/tenantId）；保存后按 SKILL.md 回读核对 content/tenantId。UI 手配保存后 content 保持 `工作表 "来源工作表名"`、formTableName/tenantId 原样留存，不自愈会一直带缺陷。

---

### 6. ⚠️ 组织架构查询条件值必须取「当前租户真实名称」（2026-09-09 实测）

ⓓⓔⓕ（selectType 4-6）`conditions` 的 `val`（realname/departName/roleName）是**等值/模糊名称**，运行时按当前租户上下文查系统表——若取值时从跨租户接口盲取「第一条」，会得到他组织的名称：能 save/deploy/回读全绿，但该名称当前租户下不存在，运行匹配不到。取值口径：

- 部门（ⓔ departName）：部门树接口**不带 X-Tenant-Id 头时返回跨组织全量树，首层根即各组织公司节点**；先 `/sys/tenant/list` 定位租户 id，**带 `X-Tenant-Id` 头**查 `queryTreeList`，从返回的该租户直属部门中取名。
- 角色（ⓕ roleName）：`/sys/role/list` **带不带租户头返回结果相同（接口不过滤）**，须在结果内按 `tenantId == 当前租户id` 严格过滤（禁止 `''/0/None` 宽匹配）——同一租户可能只有一条角色，该条才是本租户角色。
- 本文件 ⓓⓔⓕ 示例里的「张丽 / 销售 / 管理员」只是演示条件形态，**不能照抄当条件值**（环境里未必存在）。

详见 `gotchas.md` #61；接口行为见 `api-reference.md`「查询部门树 / 查询角色列表」⚠️ 段。
